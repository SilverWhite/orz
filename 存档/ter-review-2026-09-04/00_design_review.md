# TER 设计层全面审查报告（00）

> 审查人：根代理设计层切片（承接 brief_design_review.md；与 a1/a2/a3/a4
> 实现切片并行，只读静态核对）。日期：2026-09-04。
> 范围：TER M0 设计门 + M1/M2 设计规格的“设计合理性”——权威一致性、
> 参数链单一来源、可验收性/可测试性、边界与逃生阀、范围控制、治理登记。
> 基线：主仓库 HEAD 8655810；orz HEAD 901cdcc3；ADR-0010 §14.53。

## 1. 总评

设计稿本身质量良好：原则（P1–P6）、参数表（§3.1/§7）、状态机（§3.1
四步）、兜底口径（输出字节 + CPU 辅助）、三档预算、两块 live 分区契约
（T0.2 §5）、范围红线（§10 明确不做）都能机械对应到 TODO2 的步骤与
验收行；M0 门（T0.1–T0.4）的产物完整且自洽，T0.1 还主动纠正了设计稿
“schema 默认 300s”的错误口径（实为静态 120s + 描述 300/600s）。

主要问题集中在**治理登记滞后**：ADR §14.53 仍是“候选登记”，正文旧语义
（§4.5 的 300s kill_active、多处 120 轮硬限）与已闭 M1/T2.1/T2.2 的
实现并存且未登记 gap；设计稿头部状态行仍写“未实施”；T2.2 的
“no-appcontainer + allowlist 生产墙”裁决只有审计层登记，没有设计层权威
落点。这些不阻塞继续实施，但必须作为审查门放行的前置条件收口（或给出
明确的“候选过渡期”登记口径）。

## 2. 发现清单

### D-1（P1；权威一致性/治理）——ADR §14.53 候选状态与已闭实施批次的正式
裁决/gap 登记缺口

- 位置：ADR-0010 §14.53（L4306–4360 候选登记，明确“未即时取代既有设计
  语义…M1–M3 批次放行时再逐项转正”）；ADR 正文旧语义（L569 §4.5
  “Tool execution timeout 300 秒…kill_active”；L211/233/269/370/808/
  1001 “120 轮预算”等）；CLI_PROJECT_INDEX §1 AUTH-TOOL-EXECUTION-REFORM
  （`pending`）；索引 §0.1“实现偏离 ADR 时标为 gap，不得写成新设计”。
- 问题：M1（T1.1–T1.13）与 M2 T2.1/T2.2 已闭合放行，代码已按 TER 语义
  运行（默认 0 轮、auto-bg、无分层硬杀等），但 ADR 正式条款未被取代，
  也没有 GAP-* 登记表说明“哪几条旧条款正被候选过渡性覆盖、何时转正”。
  按仓库自身权威顺序（§0.1 第 3 条），当前状态下实现与冻结 ADR 的偏离
  缺一个可机械核对的登记载体。
- 证据：a1 切片 S1（10h 兜底未登记）、本报告 D-1；ADR §14.53 原文；
  T0.3 审计 §2 自述“候选不即时取代既有语义”。
- 建议：在 §14.53 或 BACKLOG2 TER-0 增“正式转正/取代清单”：
  ① 被取代的 ADR 条款行（L569；120 轮各锚点；§14.35 相关接续）；
  ② 每批次转正动作（M1 闭→§14.53 转正条目随 M2 放行门签核，或至少在
  M3 前完成）；③ 10h 绝对兜底例外句入设计稿/转正文。审查门建议以
  “转正清单落盘”为通过条件之一。

### D-2（P2；权威一致性/范围）——“no-appcontainer + allowlist 生产墙”
裁决只有审计登记，设计层无权威落点，且与 enforcement-probe 既有
AppContainer 语义（AC 基线 FAIL）产生口径张力

- 位置：TER_T2_2 audit（根因定案节）；BACKLOG2 TER-0 状态；设计稿 §4
  “AppContainer off 与 allowlist 语义不变”；AUTH-WINDOWS-HIGH-NIST
  （`partial`，入口文档 WINDOWS_HIGH_NIST_MAX_FRICTION_DESIGN）。
- 问题：这是安全姿态变化（AppContainer 空能力 compartment 吞掉 allow
  规则 → 生产墙改 no-AC + allowlist），属于 Windows 加固设计语义变更，
  但目前只写在 T2.2 审计与 BACKLOG2 流水里；TER 设计稿 §4 的“AppContainer
  off 与 allowlist 语义不变”措辞含糊，容易被后续审查误解为“AC 仍开”。
  0l 侧 enforcement-probe 的 AC 基线要求与生产墙 no-AC 的关系需要显式
  补述（AC 基线仅作对照/方法学，不再是生产墙）。
- 建议：在 WINDOWS_HIGH_NIST 设计稿与 TER 设计稿 §4 各加一行“生产墙
  定案（2026-09-03/04）：no-AC + allowlist；AC 空能力与 allow 规则不
  兼容已实证；AC 基线保留为探针对照臂”；M3 收口时并入 ADR 转正条目。

### D-3（P3；可验收性/参数链）——push 档次数上限表述三处不一致
（设计稿 §3.3 “3–4 次/run”、§10 “≤4 次/run”、实现/审计 “≤3 次/run、
verifier ≤4 兼容”）

- 建议：定单一数字——schema/verifier 上限 ≤4（机器边界），实现承诺
  ≤3（每 run 三档各一次），文档统一为“实现 ≤3、verifier 上限 ≤4”，
  删除“3–4 次”模糊表述。

### D-4（P3；参数链）——env 显式 override 与“单一生效源”的关系未在
T0.1 核对表“其它源”列显式列全

- 内容：GROK_FOREGROUND_BLOCK_BUDGET_MS / GROK_MAX_FOREGROUND_BLOCK_MS /
  GROK_IDLE_KILL_TIMEOUT_MS / ORZ_MAX_WALLCLOCK / ORZ_F6_PUSH /
  ORZ_MAX_TOOL_ROUNDS 都是显式 override（非第二默认源），语义可接受；
  建议在 T0.1 §4 表追加“override≠默认”列（a1 S7 同源，两切片一致）。

### D-5（P3；状态行滞后）——设计稿头部“状态：设计稿（未实施…）”未随
M1 闭合与 M2 进度更新

- 位置：设计稿 L4–6；对照 TODO2/BACKLOG2（M1 closed、T2.1/T2.2
  closed）。
- 建议：状态行改为“实施中（M1 闭、M2 T2.1/T2.2 闭；正式裁决待 M3
  批次放行，见 §14.53 候选）”。

### D-6（P3；可验收性）——T2.3/T3.x 验收行缺少可直接断言的事件字段与
阈值清单

- 位置：TODO2 T2.3（“单测式实机脚本证据”）、T3.1–T3.5（“journal
  证据”）；对照 T0.2 已有契约（tool_running 缺省/status=idle_killed、
  budget_cue_injected 载荷、tool_completed 三字段）。
- 建议：每个 T2.3/T3.x 验收行补“证据要点”小表（事件类型+字段+阈值，
  如 TICKS_GROWTH≥N、status=idle_killed、≤2 次 read、注入 ≤3 等），使
  实机脚本可机械判定。

### D-7（P3；边界语义登记）——“5min 无活跃兜底”文字与实现 10h 绝对兜底
的关系未在设计稿登记（a1 S1 同源）

- 建议：设计稿 §3.1 状态机第 4 步后补一句“活跃后台任务的绝对安全兜底
  =10h max_runtime（防失控泄漏，不计入评测时间窗；TER 无自身硬超时指
  分层 timeout，不排除该绝对兜底）”，供 ADR 转正引用。

### D-8（P3；设计-实现符合性待闭环项，非设计缺陷）——T0.2 §4 的
tool_running idle-kill 形态已入 schema/fixtures/verifier，但 Rust 生产
者尚未接线（详见 02 切片 M1L-1）；设计侧将其归 T1.13 门但门审计存在
过度声明

- 建议：在 M2 收口或 T3.1 前完成生产者接线，或在 BACKLOG2 显式登记为
  开放项并修正 T1.13 审计 §1.3 措辞。

## 4. 治理问题单列

1. AUTH-TOOL-EXECUTION-REFORM 状态词 `pending` 与 §0.2 定义
   （“尚无完整实现或审计闭环”）有字面错位——实现已部分闭环；建议条目
   或状态速查补“候选实施过渡期”口径（P3，登记性）。
2. 设计稿/索引/ADR 三处对“M1–M3 放行后转正式裁决”的口径一致，但缺
   “逐批转正检查表”，导致 M1 门放行后 §4.5 旧条款仍无替代记录（D-1）。
3. TER-0.1 生成器 v0.2 表对齐专项仍未启动（BACKLOG2 登记、不阻塞），
   建议 M2 收口后优先，防止夹具树手工漂移扩大。

## 5. 结论

设计层无 P0；P1 一项（D-1 治理/转正登记，作为审查门放行前置）；P2 一项
（D-2 no-AC 裁决权威落点）；其余为 P3 登记与措辞修正。建议与实现切片
发现合并后形成“审查门处理清单”，随 M2 收口批次一并处理。
