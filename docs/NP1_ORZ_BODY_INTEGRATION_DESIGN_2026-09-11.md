## 1. 目标与非目标

### 1.1 目标

1. **NP1 成为 orz 的机械身体**：模型可读一切可读、可动一切可动。感知面覆盖内核态、系统服务、结构化界面、传感器、摄像头与麦克风。
2. **指挥权留在设备**：会话、黑板、journal、门禁与时间性判断全部在 NP1；算力可外挂到 PC。
3. **入口借用系统助手位**：以系统 `ASSISTANT` 角色为主入口，支持完全无屏幕的使用路径。
4. **环境安全与稳定优先**：模型住在房子里，房子不能拆承重墙。

### 1.2 非目标（明确不做）

| 项 | 理由 |
| --- | --- |
| D2：第三方应用内部改写 | 逐应用定制、无通用解、工程量与维护成本无上限；交由社区生态 |
| 串口设备支持 | 当前无明确需求，且需要内核模块；暂缓 |
| 替换厂商登录口 | APK 层平台签名约束，且语义不匹配 |
| 修改 orz 的**模型可见工具契约**（ADR-0010 工具面） | 模型面保持冻结；身体能力一律经既有通道表达。**2026-09-12 收窄**：此非目标只覆盖「模型可见契约」；**机械层本身允许新增投影**（设备侧域 + 安卓动作/目标面，见 §3 / §9.3 / §10.2 / §10.6），该投影是本支线的交付物而非越界 |
| 云端推理以外的模型接入改造 | 不属于本支线 |

## 3. 总体架构

```text
┌──────────────────────── NP1（机械身体） ─────────────────────────┐
│                                                                   │
│  orz 会话（指挥权 / 黑板 / journal / LIF / 门禁）                  │
│      │                                                            │
│      ├─ 感知总线（PERC-*） 内核态 · 系统服务 · 无障碍树 · 传感器    │
│      ├─ 动作面（ACT-*）    root shell · 输入注入 · 应用治理(D1)     │
│      ├─ 语音域（VOICE-*）  唤醒 → VAD → ASR → 模型 → TTS           │
│      ├─ 视觉兜底           截图（文本源穷尽才允许）                 │
│      └─ 状态呈现（GLYPH-*）灯带状态机                              │
│                                                                   │
│  入口（ENTRY-*）：assist 角色（三态触发）+ 物理键兜底              │
│  凭据（CRED-*）：AccountManager + Android Keystore                 │
│  安全（SAFE-*）：承重墙规则表 + 三层安全网                          │
└───────────────────────────────────────────────────────────────────┘
              │ USB / OTG（EXT-*）
              ├─→ 安卓设备：adb（授权即近全控）
              ├─→ 电脑 / Linux：静态执行面投放 / SSH / USB 网络
              └─→ 串口设备：需要内核补驱动（暂缓）
```

设计要点：**身体层只提供"看见"与"动"，不做决策**；判定与门禁下沉到**设备侧**，票据与记账留在 **orz 软层**。即使身体层被降级或破坏，模型的行为逻辑与审计链路依然完整。

**2026-09-12 用户裁决：机械层两级化。** 机械层不再等价于「orz 里的那段代码」，而是两级（上图 `SAFE-*` 一行按此展开）：

| 级 | 承担 | 载体 | 不依赖什么 |
| --- | --- | --- | --- |
| **设备侧（下层）** | 判定 + 门禁 | SELinux 域与锁死清单、只读挂载、UID 隔离、应用治理域 | 不依赖 orz 进程存活、**不依赖模型走哪条命令路径** |
| **orz 软层（上层）** | 票据 + 记账 + 规则表治理 | ACAF、hash-chained journal、动作分级表、机械审查 | 不承担「拦住物理动作」的职责 |

理由（实测，见 [S2 机械层接入面实测](audits/0Y_S2_MECHANICAL_INTERFACE_PROBE_2026-09-12.md)）：软层判定面对安卓动作族**零拦截力**——`--allow-shell` 形态下权限门在逐命令分析面**之前**短路，承重墙命令与只读观测同判放行；写盘面也只认直接写法，`sh -c` / `eval` / `busybox` 包装即丢失。设备侧判定不看你写了什么，只看**你有没有那个权限**。

## 4. 身体层设计

### 4.1 执行宿主（`BODY-HOST-*`）

两种运行形态并存，共用同一套身体层接口：

| 形态 | 用途 | 入口 |
| --- | --- | --- |
| **交互形态** | 设备上直接使用（Termux 类终端 + TUI） | 桌面/终端图标 |
| **常驻形态** | 心跳巡检、事件响应、语音、assist 唤起 | 开机由 Magisk `service.d` 拉起 |

约束：

- 常驻进程以 root 运行，但**运行在受限 SELinux 域内**（2026-09-12 机械层两级化，§3 / §10.6）；崩溃后由看护脚本重启，不阻塞系统。
- 会话与 journal 落在设备持久目录；黑板归档与事件链沿用 orz 既有机制。
- 设备无网络授时时必须在启动自检中报错（见 `BODY-PRE-13`）。

### 4.2 感知（`PERC-*`）

**原则（写死）**：文本/结构化源能取到的，一律不许用视觉；视觉仅在文本源穷尽后使用。

| 层 | 数据源 | 内容 | 采集方式 |
| --- | --- | --- | --- |
| 内核态 | `/proc` `/sys` `tracefs` eBPF | 温控、频率、内存、进程、网络栈、电源、中断 | 轮询 + 事件 |
| 系统服务 | `dumpsys` / `service call` / binder | 活动栈、通知、连接、电信、音频焦点、传感器服务 | 拉取 |
| **结构化界面** | AccessibilityNodeInfo | 完整 UI 树（文本/控件/坐标/状态） | 常驻订阅 |
| 应用与内容 | root 文件 + 权限 | 数据库、配置、日志、媒体 | 按需 |
| 传感器 | SensorManager / HAL / sysfs | 光、距、加速度、陀螺、磁场、气压、SAR | 低频批量 + 事件升频 |
| 视觉 | `screencap` | 自绘 UI、游戏、DRM、屏幕损坏场景 | **仅按需** |

设计约束：

- 感知总线按 `(时间, 域, 事件)` 盖章进环形缓冲，模型通过 PULL 查询（近窗/趋势/取值），与既有 LIF + 黑板分区同构。
- 传感器默认低频；仅在事件或模型显式请求时升频（功耗约束）。
- 麦克风仅承担唤醒词检测；摄像头不参与心跳采集。
- **`PERC-CHANNEL-01` 通道归属（2026-09-12 S2 实测定案）**：读工具通道（`read_file` / `grep` / `list_dir`）在设备上对感知目标**全拒**（`/proc`、`/sys`、`/data/system`、`/data/data`、`/sdcard`、块设备 8/8 被读面沙箱拒——判据是「技能根 → 会话卷窗口 → workspace → 其余拒」），而权限门侧对同一路径是放行的。故**感知面经终端通道（`dumpsys` / `cat` / `getevent` / `uiautomator` / `screencap`）或专用 PULL 域**取得，不得假定读工具可达；此两层判定不一致为**登记事实**，不视为缺陷（读面沙箱是既有纪律）。
- **`PERC-VOLUME-01` 体量档（同批实测）**：单次观测 `dumpsys activity` ~16 KB、`meminfo`/`display` ~25 KB、`connectivity` ~26 KB、`service list` ~18 KB——采样频率与单轮注入预算需同批定档，禁止无条件全量拉取。
- **`PERC-UI-01` 结构化界面二选一（同批实测）**：shell 侧唯一通路是 `uiautomator dump`（**拉取式**，单次 ~1.8 KB / 5 节点，冷启动成本另计），与"`AccessibilityNodeInfo` 常驻订阅"不是同一件东西；后者需**特权应用内运行无障碍服务**，属新增执行落点，须单独立项（M2 薄壳扩展）。

### 4.3 动作分级（`ACT-*`）

| 级别 | 例子 | 门禁 |
| --- | --- | --- |
| 只读观测 | dumpsys、读 /proc、截屏、读传感器 | 默认放行 |
| 可逆动作 | 输入注入、启动应用、改设置、网络开关、权限授予/撤回 | 记账 + 可回滚 |
| 破坏性动作 | 卸载、清数据、改分区、重启 | 必须持票据（ACAF） |
| 不可逆动作 | 刷机、擦除、改身份标识 | 显式二次确认，默认拒绝 |

`ACT-KEY-01`：**以 root 运行 orz 时，现有工具面中的终端执行即等价于 root shell**，因此"彻底底层"无需扩模型工具面即可成立。

`ACT-LOCUS-01`（**2026-09-12 S2 实测追加，重要**）：`ACT-KEY-01` 成立的只是**能力**，不保证**可判定性**。实测——`reboot`、`pm clear`、`pm uninstall`、`magisk --remove-modules`、`iptables -F`、`setprop persist.sys.safemode 1`、`mount -o rw,remount /system` 在现有判定面上与只读观测**零标记同形**（`writes_real_file=false` / `exec_risk=false` / 段落仅 `NeedsPrompts`）；`sh -c` / `eval` / `busybox` 包装后写盘面**丢失**；安卓承重墙路径在"受保护编辑目标"表上**全部不命中**（该表只认桌面语义）。

故**四档分级的机械落点必须在设备侧**（§10.2 / §10.6）：软层文本分析只作为**辅助信号**，不作为拦截依据。分级表本身保留为**语义契约**（模型与规则表共用同一套命名）。

### 4.4 应用治理域（`ACT-APP-D1-*`）

模型对应用的关系被定义为**治理**（像使用家具），而非改写（`D2` 不做）。

| 想控制什么 | 机制（均已实测存在） |
| --- | --- |
| 后台运行 | `cmd appops set <pkg> RUN_ANY_IN_BACKGROUND deny`；`am set-standby-bucket <pkg> restricted` |
| 冻结 | `pm suspend`；`pm disable-user`；`pm hide` |
| 立即停止 | `am force-stop`；`am kill` |
| 权限 | `pm grant` / `pm revoke`；`cmd appops set <pkg> <OP> ignore` |
| 网络 | `iptables -m owner --uid-owner <uid> -j REJECT` |
| 后台流量 | `cmd apppolicy add restrict-background-blacklist <uid>`（实际命令为 `cmd netpolicy`） |
| 定位 | 撤权限 + appops 位置项；模拟位置需提供者组件 |
| 数据 | `pm clear`（不可逆，走票据）；root 读 `/data/data/<pkg>` |

边界（诚实记录）：device owner/admin 状态无法靠 shell 直接剥夺；系统关键组件权限属于承重墙；按 UID 封网需处理 VPN 场景。

## 5. 入口与触发（`ENTRY-*`）

### 5.1 三态触发

| 触发 | 频率 | 是否调用模型 | 职责 |
| --- | --- | --- | --- |
| 用户唤起 | 事件驱动 | ✅ | 主交互入口（assist / 语音 / 物理键） |
| 机械心跳 | 常驻低频 | ❌ 默认不调 | 采样、写黑板、累积趋势 |
| 事件唤醒 | 条件触发 | ✅ | 越界或异常时拉起模型 |

该划分与既有"机械层替模型记账、模型按需唤醒"的原则同构。

### 5.2 助手位接管

- 现状：NP1 的默认助手持有者（Google 应用）已在去预装中被屏蔽，**助手槽位为空**，无竞争。
- 方案：自建**极薄原生应用**，声明 `VoiceInteractionService` + `VoiceInteractionSessionService`，通过 `cmd role add-role-holder android.app.role.ASSISTANT <pkg>` 授予角色。
- 该应用仅承担入口与语音会话壳，业务零托管；建议置于特权系统应用位以获取特权权限。
- `ENTRY-FALLBACK-01`：**物理按键兜底** —— 通过 `/system/usr/keylayout` 覆盖（Magisk 模块，低风险）实现"长按某键 = 唤起语音"，用于屏幕损坏场景。

## 6. 语音域（`VOICE-*`）

### 6.1 流水线（全在机械层，模型面只见文本）

```text
唤醒词 → VAD 分段 → 流式 ASR → 文本 → orz 会话 → 文本 → TTS → 播放
                          ↑ 支持打断（barge-in）
```

### 6.2 轻量化选型（原型机 778G+）

| 环节 | 首选 | 备选 |
| --- | --- | --- |
| 唤醒词 | 轻量唤醒词引擎（几 MB 级） | 自训轻量模型 |
| ASR | 轻量流式本地模型 | 云端 ASR |
| TTS | 系统自带 TTS 引擎（零体积，已保留） | 极轻量离线合成（机械音可接受） |

### 6.3 由"屏幕损坏场景"反推的三条硬约束

1. 语音环路必须**完全无头**：不依赖 UI 与屏幕状态，灭屏可用。
2. 必须存在**不依赖屏幕的触发入口**（物理键）。
3. 必须有**非视觉反馈**（音频提示/震动）告知"听到/思考中/出错"。

补充：屏幕失效后，摄像头成为模型的唯一视觉通道，"按需开放摄像头"在这一场景下由省电优化升级为必备能力。

## 7. 状态呈现（`GLYPH-*`）

NP1 背部灯带天生适合作为**身体状态灯**。三级控制路径：

| 路径 | 说明 | 适用 |
| --- | --- | --- |
| 官方 Glyph Developer Kit | Nothing 官方开发者套件 | 应用层集成 |
| 社区工具 | 社区 Glyph 工具集（作曲/转换/可视化） | 素材与效果生产 |
| **root 直驱 sysfs** | `/sys/class/leds/aw210xx_led` | **路线 B 首选：无应用层依赖** |

建议的状态语义（待细化）：待机 / 心跳 / 收听到语音 / 推理中 / 需要人工介入 / 错误 / 承重墙拦截。

## 8. 凭据方案（`CRED-*`）

### 8.1 不采用"替换厂商登录口"

理由：厂商账号是外部认证依赖，且其登录组件位于 APK 层（平台签名约束）。

### 8.2 采用 AccountManager + Keystore

| 项 | 设计 |
| --- | --- |
| 账号类型 | 自建 `orz` 账号类型，注册 `AbstractAccountAuthenticator` |
| 用户入口 | 系统设置 → 账户 → 添加账户 → orz（原生流程） |
| 凭据存储 | Android Keystore（硬件保护），非明文文件 |
| 读取路径 | root 守护经 binder 获取，仅在发起请求时进内存 |
| 脱敏要求 | 事件面/journal 一律脱敏，凭据不得进入任何可回放材料 |

可选项：保险箱解封增加唤醒词或生物识别门槛。

## 9. 路线 B 的工程形态（`RTH-B-*`）

### 9.1 可行边界（关键约束）

| 目标 | 能否静态改造 | 原因 |
| --- | --- | --- |
| `/system/framework` 下的 jar（system_server 侧逻辑） | ✅ **可以** | jar 不做签名校验；ART 仅校验 dex 完整性 |
| 系统 APK（SystemUI、Settings 等） | ❌ **很难** | 平台签名约束：重新签名会失去 signature 级权限，并与共享 UID 冲突 |

**推论（重要）**：目标中的"意志"级逻辑（助手分发、电源/按键策略、输入分发、通知管控、权限决策）大多位于 system_server，即位于 jar 内 → **路线 B 的改造重心落在 `/system/framework`**，不去碰签了平台名的 APK。界面层需求改为"自建特权应用"，而非改造既有 APK。

### 9.2 承载形态

- 一切框架改造以 **Magisk 模块**形态承载：回滚 = 禁用模块 + 重启，不触碰分区。
- ART/dex 注意：补丁后首次启动会因 dex 校验变化触发重新编译，**首启变慢**并需要 `/data` 空间，属正常现象。

### 9.3 全模块化承载确认（2026-09-11 用户裁决；登记批补全）

用户裁决确认：**本支线的全部「持续性设计元素」均以 Magisk 模块承载**。本节把该裁决落成逐域对照与边界（登记前实机复核证据见附录 D）。

| 设计域 | 模块承载机制 | 模块需求 |
| --- | --- | --- |
| 常驻守护（`BODY-HOST-*`） | 模块 `service.d` 开机拉起 + 看护脚本 | 纯运行时 |
| 感知 / 动作 / 应用治理（`PERC-*` / `ACT-*` / D1） | 全部为运行时 root 命令，零系统修改 | 无 |
| 入口薄壳（`ENTRY-*`） | 模块 systemless overlay 放置 priv-app APK + `cmd role add-role-holder` 运行时授予角色 | 见登记附注 1/2 |
| 物理键兜底 | 模块覆盖 `/system/usr/keylayout` | systemless overlay |
| 语音 / 凭据 / Glyph（`VOICE-*` / `CRED-*` / `GLYPH-*`） | 纯运行时（系统 TTS、Keystore 按应用隔离、sysfs 直驱） | 无 |
| 框架 jar 改造（M5 / `RTH-B-*`） | 模块 systemless overlay 替换 `/system/framework/*.jar` | jar 无签名校验（§9.1） |
| SELinux 微调（如 eBPF 需要） | 模块 `sepolicy.rule`（Magisk 运行时注入 allow 规则） | 边界：运行时只能加 allow、不能新建类型 |

- **Zygisk 不需要**，保持关闭（与 `BODY-PRE-12` 一致）；设备现存 `nothing_debloat` 模块（去预装）即模块化承载在本机的既成事实（附录 D-05）。
- **模块外仅两件一次性基座**：M0 定版（升级至官方最终版 + 恢复 Magisk root，本支线唯一分区写入批）与 Magisk 本体（已就位 30.7）。**2026-09-12 手段更正（用户裁决；实施证据见 [M0 离线 OTA 执行记录](audits/0Y_M0_OFFLINE_OTA_EXECUTION_2026-09-12.md)）**：M0 的**升级**一半实测**不能**用「fastboot 刷官方最终版分区」——本机 `fastboot flashing unlock_critical` 被固件策略拒绝、critical 分区（xbl/abl/tz/modem 等）直刷返回 `Flashing is not allowed for Critical Partitions`，而 250701→260618 的每一级增量包均触及全部 28 个分区（含全部 critical 固件），跳过 critical 的混合刷写不成立；改用**官方签名 OTA 链**承载升级（设备自带特权应用 `com.nothing.OfflineOTAUpgradeApp`，密令 `*#*#682#*#*`，读 `/sdcard/ota/`、自行处理 `payload_properties` 后驱动 update_engine——即 critical 分区唯一被允许的更新通道）。M0 的**重新 root** 一半仍为 fastboot 刷预打补丁 boot（boot 属非 critical 分区，可写）。边界随更正收紧为：**bootloader / vbmeta / 恢复通道零触碰**；boot 分区仅在 Magisk 基座范围内写入一次（boot patch 是 Magisk 本体的必要组成，不属路线 B 的框架改造）。§10.1 承重墙「引导链（bootloader 侧）」「恢复通道」条目自动满足；「分区写入」条目由 M0 一次性盘点承担。
- **变砖风险论证**：回滚 = 禁用模块 + 重启（overlay 即刻摘除，原生系统原样启动）；最坏情况（坏 jar → system_server 崩溃循环）由下述**两条已实测通道**恢复。**2026-09-12 事实更正（M0 演练结论；证据见 [M0 离线 OTA 执行记录](audits/0Y_M0_OFFLINE_OTA_EXECUTION_2026-09-12.md)）**：本文档原写「开机按音量上键禁用全部模块」**不成立于本机**——Magisk **30.7 的 `magiskinit` 不含任何按键检测代码**，其 safe mode 判据是读取 Android 侧的 `persist.sys.safemode` / `ro.sys.safemode`（本机 `services.jar` 同用这两个属性），故「按键直接禁用模块」不是本机机制；实测三次尝试均未进入 Android 安全模式。**已实测的两条物理救援通道**：①**音量下开机 → fastboot**（本轮误触发实测成立；bootloader 级、不依赖 Android 是否可启动）——从 fastboot 可刷原厂或预打补丁 boot，等于「Android 起不来时仍能用物理键把 Magisk 拆掉或换回」；②**模块 `disable` 标志 + 重启**（需系统或 adb 可用；本轮已实测）。**登记待查项**：本机 Android 安全模式的按键组合与时序（属厂商固件行为，不阻塞 M0）；属性链路两侧均在位，若取得组合即可补测。结论仍与 §10.3「最坏结果 = 按物理键重启一次」一致，且比原表述更强（不依赖系统能否启动）。
- **易迁移性**：模块 = 一个 zip/文件夹；迁移 NP2 = 装 Magisk + 装模块 + 重跑角色授予命令，无隐藏状态。模块内容应冻结为带 SHA256 的载体工件（与 orz 三件套同批进 manifest 门禁），「模块即载体」；迁移前提 = 目标机同版本官方镜像（系统已 EOL，版本锁定为稳定因素）。

登记附注（2026-09-11，随登记批补全）：

1. privapp-permissions 白名单 xml 必须与薄壳 APK **同模块同批** overlay，否则特权权限被静默拒绝。
2. `cmd role add-role-holder` 授权可能因系统更新或清数据重置——`service.d` 开机幂等重申。
3. 附录 C 的 appops 内部名映射表随系统版本冻结；迁移跨系统版本时须重新冻结核对。
4. §14 待定项 2（验证载体）与本路线强相关：引入 NP2/模拟器时，M5 框架补丁先在验证载体走完「刷入→开机→回滚」流程纪律，NP1 只做终验（§12 表格的展开）。（**2026-09-12 已裁决：引入模拟器**，见 §12 裁决段；同日 S1 载体已建成并通过判据——**回滚原语按实测定为「AVD 目录基线副本」而非快照**，模拟器系统面只读、改系统面须走启动参数 `-writable-system` 而非 `adb remount`，判据明细见 [S1 载体搭建记录](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)。）
5. **SELinux 规则的撤销不完全跟随模块禁用（2026-09-12 S1-③ 实机实测；同日项目方裁决落地）**：模块 `sepolicy.rule` 由 Magisk 在**模块安装/更新时**汇总写入 preinit 暂存（本机解析为 `/metadata/watchdog/magisk/sepolicy.rule`），`magiskinit` 开机按该暂存文件把 allow 规则注入内核策略。实测：**「禁用模块 + 重启」只摘除 overlay 与停跑脚本，已注入的 allow 规则仍在**（策略二进制哈希不变、规则表条目仍在）；彻底撤销需**重写暂存**（安装/更新任一模块触发）或**清掉暂存文件后重启**。判据（策略哈希 + 规则全量差异恰好一条）见 [S1 载体搭建记录 §7.8](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)；S1-④ 干跑在同一载体上二次实证（含故障救援场景），面 B 回滚后规则全量 dump 与对照 dump **0 行差异**（[S1 记录 §8.6](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)）。

   **裁决（2026-09-12，项目方）**：**接受该事实、收窄设计表述，不要求改动机制。**三条落地——

   - **回滚按两个面分开、各自以机械判据收口**：面 A（框架代码）＝禁用模块 + 重启 → overlay 消失、脚本不执行、守护进程不再拉起；面 B（内核策略）＝**重写或清掉 preinit 暂存 + 重启** → `/sys/fs/selinux/policy` 哈希精确回到「Magisk 在位、无规则注入」对照值，且 `magiskpolicy --print-rules` 全量 dump 与对照 dump 差异为 0 行。§10.3 层 1 的「回滚 = 禁用模块 + 重启」按此更正为两步。
   - **不得以「模块都禁用了」为由跳过面 B**：残留物是加性 allow 规则，其作用域不随模块启用状态消失；模块停用后这些权限没有任何合法使用者，属净扩大内核允许面。
   - **实施侧硬化**：任何引入 `sepolicy.rule` 的批次，回滚清单**必含**面 B 步骤，且以「策略哈希回对照值」为放行判据——M5 干跑（S1-④）与真机每次带 `sepolicy.rule` 的模块变更同规则。
6. **规则面最小化（同批裁决）**：`sepolicy.rule` 只写当批必需的 allow 规则。理由：面 B 未执行前，残留量与规则条数成正比；且本节边界本身已限死「只能加 allow、不能新建类型」。
7. **备选机制登记（评估后不采纳，非缺口）**：把策略注入从「开机按暂存文件注入」改成「守护进程运行时 `magiskpolicy --live` 注入、随进程退出失效」——好处是禁用一个动作即撤销、不依赖面 B。否决理由：①把静态可核证的开机策略面换成随进程存活期变动的运行期面（每次开机策略都可能不同，取证与复核成本上升）；②与 §10.2「规则表人工维护、规则表本身属承重墙」的取向冲突；③Magisk 的 preinit 通道是既有机制，另造注入路径属无必要的新面。
8. **SELinux 边界重开：允许新建类型/域（2026-09-12 用户裁决，机械层两级化的落地前提）**。前六条的隐含边界是「运行时只能加 allow、不能新建类型」；该边界**不足以落实承重墙锁死**——"加 allow"是放宽方向，而锁死要的是**收窄方向**（先只给必需权限，再逐项放行）。故裁决：

   - **允许**在模块 `sepolicy.rule` / `magiskpolicy` 面**新建类型与域**，用于把模型执行的域与承重墙隔开；锁死清单按**类型/标签**表达（不按路径名——S2 实测：模拟器 `by-name` 下无 `boot` 节点，分区名随机型而异，字面路径匹配本来就不成立）。
   - **前提三条**：①任何域变更**先在模拟器载体干跑**（S1 已就绪，坏结果 = 还原 AVD 基线副本）；②域内**必需权限用实测产出**（拒绝日志驱动的 allow 清单，不拍脑袋）；③回滚面 B 判据不变（策略哈希回「Magisk 在位、无规则」对照值 + 规则全量差异 0 行）。
   - **风险登记（诚实）**：窄域写错轻则守护进程不可用、重则影响开机；新建域比"只加 allow"的取证面更大（类型、属性、域转换三处都要进留档）。故本项**不改变 §10.3「最坏结果 = 按物理键重启一次」**，且域的每一项变更都按 M5 管线纪律处理。
   - 边界：本次重开仅覆盖**本支线自用**的类型/域；不改系统预置域（§10.1「系统完整性」条目的其余部分不变）。

## 10. 安全设计（`SAFE-*`）

### 10.1 承重墙清单（禁止改动/禁止模型触碰）

| 类别 | 内容 | 原因 |
| --- | --- | --- |
| 分区写入 | 块设备写入、`mkfs`、`remount /system`、fastboot 擦写 | 直接毁镜像 |
| 引导链 | boot / bootloader / modem / vbmeta | 变砖 |
| 系统完整性 | 改系统分区实体文件、改系统**预置** SELinux 域、清 ART | 起不来（**例外通道**：模块 `sepolicy.rule`——允许加 allow 与**本支线自用**的新建类型/域；回滚必含策略回滚面 B，见 §9.3 附注 5–8） |
| **模型自身存活** | 使系统长期离线、或让自己在**无人工介入**时无法自动上线（典型：进入 fastboot/bootloader、断掉自身启动链路、破坏恢复通道） | 自杀。**2026-09-12 用户裁决修订**：模块面（启用 / 禁用 / 内容）**不再整体列为承重墙**，模型可自行操控——模块出错时重启即可让系统恢复；**唯一不可逆档 = 进入 fastboot**（进去了模型自己也起不来） |
| 身份与账户 | IMEI / 序列号 / FRP 标记 | 不可恢复 |
| 恢复通道 | 破坏 fastboot 可达性、覆盖回滚镜像 | 断掉唯一救命绳 |

### 10.2 确定性拦截（机械层·设备侧）

**2026-09-12 用户裁决 + S2 实测更正**：拦截不再建在 orz 的文本分析面上，而是建在**设备侧**——拦截位置必须在模型执行路径**之下**（内核策略 / 只读挂载 / UID 隔离 / 应用治理），判据从「命令写了什么」改为「**有没有那个权限**」。

- 对动作与目标做**规则匹配**：目标以 **SELinux 类型/标签 + 挂载点/设备属性**表达（**不按字面路径名**——S2 实测：模拟器 `by-name` 下无 `boot` 节点、分区名随机型而异，字面匹配本来就不成立），命中即拒或升级为票据。
- **禁止把"全放行终端"当作身体部署形态**：`--allow-shell` 形态下权限门在逐命令分析面**之前**短路，实测承重墙命令与只读观测同判放行（S2 面 A）。身体以**受限域 + 白名单动作通道**运行。
- 软层文本分析（bash 词法 / 写盘面 / 执行风险）降级为**辅助信号与审计证据**，**不作为拦截依据**（`sh -c` / `eval` / `busybox` 包装即失效，S2 面 B）。
- 规则表人工维护，**规则表本身属于承重墙的一部分**；锁死清单与开放清单见 §10.6，域内每项权限按 §9.3 附注 8 前提②用**拒绝日志实测**产出。
- 无模型参与：拦截是机械的、模式化的、可预期的。

### 10.3 三层安全网

| 层 | 手段 | 效果 |
| --- | --- | --- |
| 1 | Magisk 模块承载全部框架改造 | 回滚 = **两步**：面 A 禁用模块 + 重启（overlay 摘除、脚本停跑）；面 B 若本批引入过 `sepolicy.rule`，须**重写或清掉 preinit 暂存 + 重启** → 判据 = 策略哈希回「Magisk 在位、无规则」对照值且规则全量差异 0 行（2026-09-12 裁决，见 §9.3 附注 5–7；S1-④ 二次实证见 [S1 记录 §8.6](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)） |
| 2 | **物理键可达的救援通道（2026-09-12 更正）**：开机按音量下 → fastboot（已实测，不依赖 Android 可启动）→ 刷原厂/预打补丁 boot；另有模块 `disable` 标志 + 重启（已实测，需系统或 adb 可用） | 改砖也能靠物理键救回（原写「Magisk 安全模式（音量上）」，本机 Magisk 30.7 无该机制，见 §9.3 更正） |
| 3 | boot 分区 A/B 双槽 | 引导层问题可切槽 |

结论：**框架改造的最坏结果应被限制为"按物理键重启一次"**。

### 10.5 防滥用边界（2026-09-12 用户裁决；登记批补全）

**裁决**：本支线**不引入任何「防持有者滥用」的强制机制**，也**不做目标机侧的通告与许可流程**。2026-09-12 评估过的提案逐条否决并登记理由，本节的作用是让后续检索直接命中结论——**不得作为缺口重新立项**。

| 被评估提案 | 判定 | 理由 |
| --- | --- | --- |
| 鉴权代码被编辑即**锁死**框架 | 否决 | self-DoS——惩罚对象是使用者本人；正当事务即可误触发（模块禁用/更新、备份恢复、系统升级） |
| 鉴权代码被编辑即**自毁**框架、强制回仓库重装 | 否决 | 违反 §10.1 承重墙（模型自身存活）、§4.3 动作分级（不可逆动作默认拒绝）、§10.3（最坏结果 = 按物理键重启一次）与 §9.3 回滚路径（禁用模块 + 重启）；自毁会先销毁取证面（hash-chained journal）；误报源已知存在（`BODY-PRE-13` 无网络授时的时间回退、OTA 后 dex 重编译、boot 重打补丁） |
| 「确保鉴权不可跳过」 | 不可达 | 被防对象即设备的 root 持有者；在已解锁 + root（`BODY-PRE-12`）前提下，本地不存在不可绕过的软件强制；该能力本身不依赖 orz（现成调试/自动化工具同样可用），加固 orz 不降低危害总量；源码公开且可自行构建 ⇒ 客户端自校验在数学上无意义 |
| 外控时目标机**锁定 + 响铃 + 弹窗**（提示可能是攻击） | 否决 | 触发动作由载体机发出 ⇒ 载体机不发则机制不存在，对攻击者零约束；「锁定 + 响铃 + 弹窗」本身即骚扰/致瘫原语；弹窗若做定性指控则可被伪造且可能构成误导；目标机未设锁屏时该机制恰在最需要的目标上失效 |
| 目标机**许可流程**（一次性/限时授权 + 持续可见提示） | 否决 | 落点依赖目标机装有本组件，而最需要保护的目标（陌生人 / 未安装方）没有落点；残余价值（把「静默控制」改成「须动手改包」）不足以抵偿新增的执行落点与攻击面 |

**边界声明**：既有内部鉴权与防篡改——权限判定 fail-closed、ACAF 票据、hash-chained journal 与签名、运行守卫、工作区沙箱——覆盖的威胁是**使用者自身资产与审计链被误操作、越权或伪造**；它对「持有者危害第三方」**不做任何断言**，且作者侧**无法约束**。故本项属**范围外的已裁决边界，不是缺口（gap）**：登记时不得写成待办、缺口或未决项。

**保留的最小纪律**（均为既有性质点名，不新增机制）：

1. `EXT-*` 外部控制动作**不豁免记账**——沿用 §4.3 动作分级，外部控制与本地动作同待遇。
2. **不做「以便捷为名降低目标侧可见性」的特性**——不提供静默/隐蔽式控制的便利。
3. **前提与责任**：外部控制以目标侧授权为条件（§11 前提列），责任在操作者；项目侧不做约束承诺。

### 10.6 存在底线与锁死清单（2026-09-12 用户裁决）

**裁决原则（机械化表述）**：本支线的安全范围**以"模型意志存在"为底线**——模型可以在系统中操控整部手机，但**不得做杀灭系统、使系统长期离线、或让自己在无人工介入时无法自动上线的操作**；其余全部开放。

**为什么这条底线成立**：模型与框架都依赖系统存活才能启动。因此"系统能起来"不是对模型的额外约束，而是模型**自身存在的前提**。把边界画在"模型还能继续做事"的位置上，它既不对第三方负责（§10.5 已裁决不承诺），也不停留在资产层面，而是对**框架自身可运行性**负责。

**判据（逐条动作、机械可核验）**：执行前必须能回答——「这一步之后，是否存在一条**不依赖人工**的路径，让系统与守护进程重新上线？」答否 → 拒，或升级为需人工票据。典型否例：进入 fastboot/bootloader（模型自己回不来）、写引导链或分区、破坏恢复通道、清空自身启动链路。**注意"系统能重启"与"模型能回来"是两件事**：禁用承载自身启动的模块后，系统照常起来，但模型不再上线——该情形按否例处理。

**锁死清单（对模型不可达；设备侧域内不给 allow）**：

| 面 | 内容 | 表达方式 |
| --- | --- | --- |
| 引导链 | boot / bootloader / vbmeta / modem 等 | SELinux 类型 + 块设备属性 |
| 分区写入 | 块设备写入、`mkfs`、`mount -o rw,remount` 系统分区 | 域内无对应 allow |
| 系统完整性 | 系统分区实体文件、系统预置域、ART 清空 | 只读挂载 + 域约束 |
| 恢复通道 | fastboot 可达性、回滚镜像 | 对模型不可达；**对人类操作者保留** |
| 身份与账户 | IMEI / 序列号 / FRP 标记 | 域内无对应 allow |

**开放清单（对模型可达；走票据 + 记账）**：

| 面 | 内容 | 约束 |
| --- | --- | --- |
| **模块面** | 模块的启用 / 禁用 / 安装 / 卸载 / 内容 | **唯一"自伤可自愈"面**：模块出错时重启即可让系统恢复（用户裁决口径）。操作前按存在底线判据自查"重启后能否自动上线"；**承载自身启动的模块属临界项**，须先确保备用启动路径或改走人工票据 |
| 应用治理域 | `appops` / `pm` / `am` / UID 断网等（§4.4） | 可逆档记账；破坏性（清数据 / 卸载）走票据 |
| 感知与状态呈现 | 感知总线 / Glyph / 语音（§4.2 / §6 / §7） | 只读或可逆 |
| 外部身体 | OTG+adb / 执行面投放（§11） | 前提与责任见 §11 |

**与既有边界的关系**：§10.5 管的是"持有者会不会拿它危害第三方"（**不做约束承诺**）；本节管的是"模型会不会把自己弄死"（**硬约束**）。两者互补。**诚实标注**：设备持有者本人是 root，仍可自行加规则或换域——本节的"锁死"是**对模型在正常执行路径上**锁死（S2 实测已证明软层面这条路上拦不住），不是密码学意义上的不可绕过，与 §10.5 对"本地不存在不可绕过的软件强制"的既有裁决一致。

**物理兜底（已实测）**：模型若因模块操作导致自己起不来，人类操作者用音量下 → fastboot 即可救回（M0 救援通道演练，§9.3）；故模块面的开放不构成断线风险。

## 11. 外部身体（`EXT-*`）

`EXT-BOUNDARY-01`（2026-09-12 裁决）：**外部控制不做目标机侧的通告、锁定与许可机制**；被控端可见性以目标侧自身设置为准。边界与理由见 §10.5。

| 目标 | 通道 | 结论 | 前提 |
| --- | --- | --- | --- |
| 安卓设备 | USB OTG + adb | ✅ 近全控 | 目标开放 USB 调试并授权 |
| 电脑 / Linux | 静态执行面投放 / SSH / USB 网络 | ✅ 可控 | 目标侧有可达服务或允许投放执行面 |
| 串口设备 | USB 转串口 | ❌ 当前不可 | 内核缺 `USB_SERIAL`（暂缓） |

`EXT-SEED-01`：**静态执行面投放** —— 把 orz 静态三件套投放到目标（aarch64 安卓已验证；x86_64 PC 用既有 linux 发布包），目标即从"被摆布的设备"升级为"另一个 orz 身体"。

| 载体 | 能验证 | 不能验证 |

**2026-09-12 用户裁决（§14.2 定案）**：**引入模拟器为常设验证载体**，验证载体集 = 模拟器（新增、常设）+ NP2（既有，流程纪律）+ NP1（端到端终验）。模拟器承担两件事：①自有代码验证——守护进程、IPC、协议、工具层、语音流水线；②M5 补丁**流程纪律干跑**——「打补丁 → 进系统 → 开机 → 回滚」全程在模拟器先走通，把 §10.3「最坏结果 = 按物理键重启一次」再压低一档。边界不变：AOSP 镜像与 Nothing 系统不是同一份代码，模拟器**不验证厂商框架与 NP1 专属内核面**（Glyph 硬件、NP1 内核 config、平台签名行为）。

**技术形态与回滚原语（2026-09-12 S1 实测定案；判据明细见 [S1 载体搭建记录](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)）**：

| 项 | 定案 |
| --- | --- |
| 系统镜像 | `system-images;android-35;aosp_atd;x86_64`（Android 15 的 AOSP ATD 无头自动化镜像，与本机 Android 15 对齐）。选 AOSP 变体而非 Google APIs 变体：本支线验证的是我们自己的代码，不需要 Google 服务面 |
| 模拟器与工具链 | Android Emulator 37.1.11.0 + cmdline-tools 19.0；AVD `orz_body_a35`（4 核 / 2 GB RAM / 数据分区 6 GB / 无 GPU）；宿主硬件加速走 **WHPX**（模拟器官方自检 `installed and usable`）；工具链与虚拟设备**全部落宿主 D 盘**（本机 C 盘可用空间不足 2 GB，为搭建硬约束），Java 临时目录同批重定向 |
| orz 载体 | **直接复用当前冻结的 x86_64 musl 三件套**（S1 时为 **0.4.3**；静态 ELF 在安卓内核直接执行，与 `BODY-PRE-01` 的 aarch64 同理，**无需新构建**）。实测 `INTERP=0` / `NEEDED=0`、主机↔设备 SHA256 逐件吻合、三件均在 Android 15 内核上实际执行——`BODY-PRE-01` 的 x86_64 对应判据成立 |

| 改系统面的方式 | 模拟器上 `/` 与 `/vendor` 为只读，`adb remount` 被拒（`Device must be bootloader unlocked`），须走启动参数 `-writable-system`（本镜像非 Play Store 变体，符合条件）——与 NP1 的 Magisk systemless overlay 同族但机制不同 |

**S1 四项全部完成（2026-09-12）**：①无头镜像搭建 ②orz 载体上机冒烟 ③Magisk 模块打包 / 安装 / 禁用 / 恢复实机化演练（含遗留项：`PREINITDEVICE` 与 SELinux 规则注入闭环）**④M5 补丁「打补丁 → 进系统 → 开机 → 回滚」流程纪律干跑首轮**。③ 的附带实测发现「禁用模块不撤销已注入规则」已裁决落地（见 §9.3 附注 5–7）；④ 的产出是**三条管线纪律 + 一条验收判据**，登记于 [S1 载体搭建记录 §8.7](audits/0Y_S1_EMULATOR_CARRIER_SETUP_2026-09-12.md)：

1. 管线必须产出**可复现**（两次构建同哈希）、**可逐条字节核对**（改动面：反编译树差异 + ZIP 条目双面）且满足平台装载前提（**ZIP 条目数据 4 字节对齐**）的产物——首版产物未对齐时 ART 会报 `Can't mmap dex file … please zipalign to 4 bytes` 并退化为解压装载（本轮已实测并修正）。
2. M5 补丁的验收**必须单列「补丁件在运行期真的被采用」的判据**：实测一个被打坏的启动类路径件**不会**导致系统起不来，而是被 ART 记告警后在运行期**静默丢弃**（`zygote` 映射数 0）——只核"文件落位"会把这一档放过去；真正的"起不来"档要在**开机必需件**（系统服务自身依赖的 `services.jar`）上才会出现，救援通道 = 模块 `disable` 标志 + 重启（模拟器故障态下 adb 仍可用；真机侧对应音量下 → fastboot）。
3. 回滚是**两步**（面 A 框架代码 + 面 B 内核策略），判据与口径见 §9.3 附注 5–7；整体回滚仍是「还原 AVD 目录基线副本 + 重启一次」（本轮实测 26.4 s 起完）。

**S2 机械层接入面实测（2026-09-12 同日，记录见 [S2 实测](audits/0Y_S2_MECHANICAL_INTERFACE_PROBE_2026-09-12.md)）**：软层判定面对安卓动作族**零拦截力**（三条——① `--allow-shell` 短路发生在逐命令分析面之前；② `reboot`/`pm clear`/`magisk --remove-modules`/`iptables -F` 等零标记、与只读观测同形；③ 读工具通道对感知目标 8/8 全拒）。该结论直接改写了 §3 / §4.2 / §4.3 / §10.1 / §10.2，并新增 §10.6。

**由此新增两项验收判据（本支线必须过）**：

1. **承重墙拒绝率**：对 §10.6 锁死清单的 N 条样例动作，在**模型实际可达的域**里逐条尝试，拒绝率必须 **N/N**（任一放行即不通过）；样例集须含直接写法与 `sh -c`/`eval`/`busybox` 包装写法。
2. **自动上线判据**：任一开放面动作（尤其模块面）执行后，必须存在**不依赖人工**的路径让系统与守护进程重新上线，且在模拟器上逐条核验（坏结果 = 还原基线副本）。

## 附录 C：应用治理命令实测形态（可直接复用）

以下形态均于 2026-09-11 在 NP1 上确认可用；**以本附录为准**（正文表格中"后台流量"一项的写法以本附录为准）。

```sh
# 后台限制
cmd appops set <pkg> RUN_ANY_IN_BACKGROUND deny
am set-standby-bucket <pkg> restricted      # active|working_set|frequent|rare|restricted

# 冻结 / 停用 / 隐藏
pm suspend <pkg>
pm disable-user <pkg>
pm hide <pkg>            # 与 unhide 配对

# 立即停止
am force-stop <pkg>
am kill <pkg>

# 权限
pm grant <pkg> <permission>
pm revoke <pkg> <permission>
cmd appops set <pkg> <OP> ignore            # OP 名为 appops 内部名（如 FINE_LOCATION）

# 后台流量限制（UID 维度）
cmd netpolicy add restrict-background-blacklist <uid>

# 按 UID 断网（root）
iptables -A OUTPUT -m owner --uid-owner <uid> -j REJECT

# 清空应用数据（不可逆，走票据）
pm clear <pkg>
```

实现备注：`cmd appops` 的操作名使用系统内部名（例如位置为 `FINE_LOCATION` / `COARSE_LOCATION`），不是权限字符串，封装时需维护一张名称映射表；该映射表随系统冻结后可静态固定，迁移跨系统版本时须重新冻结核对（§9.3 登记附注 3）。
