## 1. 背景与问题

### 1.1 实测命中率

- DeepSeek 控制台（2026-08-18）：总命中 8,845,056 / 总未命中 4,279,939 /
  总输出 308,997 → **命中率 ≈ 67.4%**。
- TB2 复验（`D:\tb-eval\jobs\2026-08-17__23-29-44`）：66.5%，80 次请求
  18 次 `request_header_change` 全为 system 变化——状态行根因已于 ba86910
  修复（ADR-0010 §14.25）。但 **header 变化之外的请求视图重写**此前未审计，
  本次调研定位到动作台账折叠。
- 目标：日常命中率 ≥ 90%（DeepSeek 涨价后命中价约为未命中价的 1/30，成本
  敏感；官方称 95–99% 可行，dsh 实测 80–85%）。

### 1.2 有效窗口 384K 的出处（2026-08-18 复核补精确）

- 出处：**DeepSeek V4 技术报告**《DeepSeek-V4: Towards Highly Efficient
  Million-Token Context Intelligence》（arXiv:2606.19348）Figure 9 的
  MRCR-8-needle / Average MMR 检索质量曲线——即 orz 当前使用的 V4
  （flash/pro）自身，不是旧版。数据点来自论文 SVG 矢量源逐点读取
  （`assets/mrcr.svg`，ar5iv 镜像），非目测。
- 模型规格：V4 **输入上下文 1M token、最大输出 384K token**；论文 §5.3.1
  评估设置：Non-think / High / Max 推理档上下文窗口分别为 8K / 128K /
  384K（agent 任务上限 512K）。orz 用 `deepseek-v4-flash` + EnabledMax
  → 对应 **Max 档**。
- Figure 9 精确数据点（MRCR-8-needle，Average MMR）：

  | 上下文 | V4-Pro-Max | V4-Flash-Max（orz 实际模型） |
  |---|---:|---:|
  | 8K | 0.900 | 0.910 |
  | 16K | 0.850 | 0.840 |
  | 32K | 0.940 | 0.870 |
  | 64K | 0.900 | 0.850 |
  | 128K | 0.920 | 0.870 |
  | 256K | 0.820 | 0.760 |
  | 512K | 0.660 | 0.600 |
  | 1M | 0.590 | 0.490 |

  （此前登记的「8K≈0.90、32K≈0.94、128K≈0.92、512K≈0.66、1M≈0.49」为
  Pro 曲线（前三项与 512K）与 Flash 曲线（1M=0.49）的混合读数；本次拆分为
  两档独立精确序列，并补上 16K/64K/256K 三个中间点。）
- 128K–512K 斜率分析（2026-08-18 用户问询「找相对收益最大点」）：两档一致，
  **128K→256K 是 128K 之后下滑最快的区段**——Flash 0.870→0.760
  （Δ=−0.110，斜率 ≈ −0.00086/K）、Pro 0.920→0.820（Δ=−0.100，
  斜率 ≈ −0.00078/K）；256K→512K 放缓（Flash 0.760→0.600、Pro
  0.820→0.660，均 ≈ −0.00063/K）。即质量拐点不在 512K，而在
  128K–256K 之间。
- **参数定案（2026-08-18 用户裁决，统一参数、不做跑分特化）**：折叠推进
  `fold_trigger_tokens` = **128K**（MRCR 平台期边界 Flash 0.870，模型带
  原文工作的窗口不超过质量平台期；本仓库开发场景多文档读取需求——
  index 30.5K / ADR 43K / BACKLOG 27.8K 全量 ≈101K + preamble 8K，
  128K 原文窗口允许连续读完关键文档集不被折叠打断）；压缩普通触发
  `trigger_tokens` = **192K**（陡降段内、Flash ≈ 0.81，压缩周期比 96K 长
  约 40%，见 §4/§5）；压缩兜底 `safety_tokens` = **256K**（Flash ≈ 0.76，
  仍明显高于 512K 的 0.60；异常强制线，与普通触发间隔 64K 宽裕）。
- 校准结论：orz 的「有效窗口 384K」= Max 档官方评估窗口（论文 §5.3.1），
  对应 Flash 插值 MMR ≈ 0.68（256K=0.760 与 512K=0.600 之间）——是
  512K 之前的保守质量线，**不是模型的输入硬上限**（输入上限 1M）。
  「legal max=384K」措辞与 V4 的 max output 384K 同数，2026-08-18
  澄清为质量线而非输入限制；不做新 live probe 的决策不变。

### 1.3 根因：动作台账折叠滑动窗口

`action_ledger::build_collapsed_request`（[action_ledger.rs](D:/CLI/orz/crates/orz-loop/src/action_ledger.rs:214)）
在**每次模型请求前对整个消息历史无状态重算**折叠边界：保留最近 `tail`（默认
2）轮原文，更早的完整轮次压成 `[动作台账 v0.1]` 行
（[agent_loop.rs](D:/CLI/orz/crates/orz-loop/src/agent_loop.rs:1197)）。
每轮请求时历史多出一个完整轮次 → 折叠窗口滑动 → **请求前缀被重写**。

复刻 `action_ledger` 逻辑的模拟（tail=2，每轮 = 声明 + 结果 + 回复）：

| 请求 | 与上一请求前缀重合率 | 事件 |
|---|---|---|
| req2–3 | 100% | 轮次不足，不折叠 |
| req4 | **1.5%** | 首次折叠：早期轮次整体替换为台账行 |
| req5 | 49.7% | 台账增行 + 再移除一轮原始记录 |
| req6–11 | 63% → 84% | 每轮滑动，持续部分重写 |

真实场景中，被替换的是早期数万 token 的完整工具记录（大文件读取信封、网页
抓取结果等），**每次滑动基本全量 miss**——这是 67% 命中率的主要解释。

TB2 实测视图增长（`D:\tb-eval\jobs\2026-08-17__23-29-44`，80 次模型请求）：
折叠视图从 2,082 token 线性涨到 130,020 token，平均 **≈1.62K/轮**
（台账行保留每轮「最终回复」原文 verbatim，为增长主体）；本次 130K 低于
170K 阈值故未触发压缩。该速率用于 §5 压缩周期（192K ≈ 71 轮）与命中率估算。

`CONTEXT_COMPACTION_DESIGN_2026-08-14.md` §3 明确写了「每个模型工具轮完成后
坍缩、不设冷却」——**设计意图与实现一致，但与 v1.9 前缀缓存纪律（ADR-0010
§3.5 条 6）冲突**：2026-08-14 定稿折叠时，尚未把「请求视图字节级前缀稳定」
纳入约束（当时只保证了 header 指纹与系统提示词静态）。

### 1.4 对照 DeepSeek Harness（dsh，源码证据）

dsh 的核心纪律是「平时严格追加，压缩才一次性 replace」：

- 每次请求从 session 日志派生 messages，投影带缓存：每个 surface 节点只投影
  一次，代价 O(新增节点)；只有压缩 `replace` 才重建整个派生数组
  （`packages/core/session/src/index.ts` deriveMessages / `surface.ts`）。
- 动态运行时上下文也是**追加**：变化时作为新 user 消息追加（"This snapshot
  supersedes earlier runtime-context snapshots"），从不改写历史
  （`packages/core/agent-loop/src/runtime-context.ts`）。
- 系统提示词为注册制 sections 按固定 order 拼接；工具 schema 稳定排序；
  header 指纹只在 system/tools/config 变化时记录。
- 压缩是显式、低频、一次性的替换，之后继续追加。
- key-gated 真实 API e2e 断言**每个后续请求** `cacheReadTokens > 0`
  （`packages/core/agent-loop/tests/request-cache.e2e.ts`）。
- 上下文压力控制（压缩触发）：`compaction-basic` 的
  `DEFAULT_THRESHOLD_RATIO = 0.8`——**压缩触发 = 模型窗口的 80%**（对 V4 的
  1M 窗口即 800K，社区实现已指出该值超过质量塌陷点，为 V4 另设 384K–512K
  soft budget）；`DEFAULT_RETAIN_RATIO = 0.16`（压缩后保留原文尾 = 窗口
  16%）；摘要输出上限 8192 token；trigger 分 `pressure`（正常压力）与
  `context-overflow`（provider 确认溢出强制）。**dsh 没有 orz 这种零模型
  调用的机械台账层**——其上下文控制只有「追加 + 一次性摘要压缩」，故折叠
  阈值无官方先例可套，只可类比其「相对窗口比例」的思考方式。

orz 已对齐的部分：系统提示词完全静态（ba86910 后）；状态行变化才追加
（§14.25）；反例门/定向询问/预算块等尾部注入全部追加式；工具投影顺序稳定
（base 顺序 + BTreeMap 探针）；压缩低频一次性 replace。**未对齐的正是折叠的
每请求无状态重算**——本文修订。

### 1.5 已排除项（不设机制）

- **TTL**：社区 5 小时说法 + 长任务实际正常命中（用户体感）→ 非现实风险；
  若未来出现跨小时停顿可再评估，本轮不设 TTL 相关机制。
- **工具翻转**：已知接受事件（v1.9：探针真实变化即全量 miss，第二轮自动恢复）。
- **尾部注入模板**：追加式，不破坏前缀。
- **系统提示词**：完全静态，无时间戳等动态文本。
- **辅助模型请求**（摘要/预检）：固定 header + 独立输入，不干扰主链。

## 2. 设计目标与边界

- 目标 1：两次折叠推进之间，请求视图前缀**字节级稳定**（纯追加）。
- 目标 2：日常命中率 ≥ 90%（成本估算见 §6）。
- 目标 3：保留台账层上下文控制（模型注意力不稀释）与零模型成本特性。
- 目标 4：审计双轨不降级——journal/sidecar 保留完整工具记录；折叠视图
  仍是只读投影。
- 边界：不改探针语义（v1.8/v1.9）；不改 50K 单轮注入预算；不改压缩审计
  契约（`context_compressed` 事件 / marker / 存档 / digest）；不改协议安全
  （整轮配对、无孤儿 tool result）；不改 README 冻结版本表述。

## 3. 核心机制：折叠点状态化（FUS-LEDGER-FOLD-STATE）

### 3.1 状态

`AgentLoopController`（会话级）新增：

```text
fold_start: Option<usize>   // 折叠起点消息索引（第一个工具声明），None = 未折叠
fold_cut:   Option<usize>   // 已折叠覆盖的闭端消息索引；保留区间 = [fold_cut..] 原文
folded_ledger: Option<String> // 冻结台账块文本（推进时一次性渲染，之后不变）
```

不变量：`fold_start < fold_cut`；两者同时为 Some 或同时为 None；`folded_ledger`
非空当且仅当状态已折叠。

> 实施注记（2026-08-18 审查收口）：折叠三态为**每轮循环实例局部**（随
> `LoopOutcome` 返回），而非字面的 controller 会话级字段——同一 controller
> 被主车道与嵌套检索子代理共用，共享字段会被子代理调度污染；语义等价（每次
> 循环起始 fold=None 重新累积，与 §3.6「恢复后重新累积」一致，恢复后首次
> 推进重写一次前缀为接受的低频成本）。

### 3.2 请求视图构建（取代无状态重算）

每请求前：

- 未折叠（`fold_cut = None`）：视图 = `messages`（与现状前几轮相同，不折叠）。
- 已折叠：视图 = `messages[..fold_start]`（preamble）+ `folded_ledger`（user
  消息）+ `messages[fold_cut..]`。

推进之间，`fold_start` / `fold_cut` / `folded_ledger` 全部不变，新轮次只追加
在 `messages[fold_cut..]` 之后 → **请求视图 = 上一请求视图 + 追加**，前缀
字节级稳定。

`build_collapsed_request(messages, tail)` 的无状态形态保留给摘要输入等辅助
路径使用前先迁移到有状态视图（见 §3.5），不再作为主请求的唯一构建路径。

### 3.3 推进触发（低频、机械、零模型调用）

- 时机：每请求前用 `estimate_messages_tokens` 估算视图 token，≥
  `fold_trigger_tokens`（默认 **128,000**，2026-08-18 定案由 64K 上调；
  可配 `ORZ_FOLD_TRIGGER_TOKENS`）时，在工具轮间隙（loop-top，与压缩同
  纪律：不打断当前批次、checkpoint 轮优先）执行推进。
- 动作（一次性）：
  1. 收集 `messages[..保留起点)` 中全部完整轮 → 生成台账行（轮次号延续旧
     冻结台账的最后轮次）；
  2. `folded_ledger` = 旧台账行 + 新增行（重新渲染一次，冻结）；
  3. `fold_cut` = 新保留起点（最近 `tail` 轮起点）；`fold_start` 不变。
- 无完整轮可折叠时不推进（防空转；保留起点推进逻辑复用 `collapsed_cut`
  的整轮配对纪律）。
- 推进 = 一次前缀重写（每窗口一次，接受；窗口内其余请求全部命中）。
- 推进留痕（2026-08-18 审查收口）：每次**真实推进**（非防空转 no-op）写入
  v0.2 事件 `ledger_fold_advance`（`fold_start`/`fold_cut`/`rounds_folded`/
  `view_estimate_tokens`/`agent_role`）——`request_header_change` 只跟踪
  system/tools/config 摘要，折叠推进造成的前缀重写此前无法经事件面归因；
  该事件使每窗口一次的 miss 可定位（配合 provider 缓存统计分窗口核对）。
- 推进不改变 `messages` 本体（journal/sidecar 完整记录保留，审计双轨不变）。

### 3.4 tail 语义

保留最近 `tail` 轮原文（默认 2，沿用 `DEFAULT_RECENT_TAIL_ROUNDS` /
`recent_tail_rounds`，可配），与现状一致；`tail` 属于「推进时保留原文的轮数」，
不因状态化改变。

### 3.5 与压缩联动

压缩执行时（rhythm 192K / fallback 256K / session_end）：

1. 旧冻结台账归档：追加到本次摘要存档 markdown（与旧 marker 同纪律——滚动
   单 marker，旧内容进存档），`messages` 中只保留压缩 marker；
   **2026-08-18 审查收口已实施**：成功分支把 `folded_ledger` 以
   「折叠台账（冻结快照）」代码段追加进存档（`summary_archive_markdown`）；
   终止态（摘要重试失败）无归档文件、台账不落盘——登记为接受边界（journal
   事件仍保留原始工具记录，台账可确定性重推导）。
2. drain `[第一个工具声明 .. 保留起点)` + 插入 marker（沿用现状
   `run_template_compact` 逻辑；保留起点基于 `fold_cut` 而非重算 tail）；
3. `fold_start` / `fold_cut` / `folded_ledger` 重置为 None（marker 之后重新
   累积）。

摘要输入（`run_template_compact` 的 `summary_input`）改与主请求同一有状态
折叠视图（同源，不单独重算），控制摘要调用成本的同时保持一致性。

### 3.6 恢复路径

- `fold` 三态为运行期内存状态，不持久化；
- 恢复加载 conversation 后均为 None；恢复预检（D2-2）截断后自然从截断点
  重新累积；
- 恢复后首次推进会重写一次前缀（低频，接受）。

的测量口径为「请求前估算（视图）」——两口径均以**折叠视图**为准，写入文档
避免混淆。**session_end 终局清理例外**（2026-08-18 审查收口显式区分）：主/
检索车道 session_end 沿用「全量 conversation 估算」门槛（既有语义，压缩折叠
视图之外的完整持久化内容），不属上述 loop-top 两口径。

## 5. 命中率与成本估算（复刻模拟，F = 128K / T = 192K）

假设每轮净增 1.5K token（TB2 实测折叠视图增长 ≈1.62K/轮，见 §1.3 口径），
推进后回落至约 15K（preamble + 冻结台账 + tail），窗口 15K→128K：

- 方案 A（本设计）：约 75 轮窗口，总输入 ≈ 5.4M；miss ≈ 推进 128K + 75×1.5K
  追加 ≈ 241K；**命中率 ≈ 95.5%**（≥90% 目标）。
- 现状（每轮滑动）：同窗口 miss ≈ 75×20K ≈ 1.5M；命中率 ≈ 72%（控制台实测
  67.4%，口径含 header/工具翻转等其他因素）。
- 成本（v4-flash：miss $0.22/1K、hit $0.007/1K）：方案 A ≈ $89 / 窗口
  （≈ $1.18/轮）；现状 ≈ $357 / 窗口（≈ $4.76/轮），**约为现状的 1/4**。
- 压缩（192K，≈71 轮/次）执行时台账归档重写视图，每压缩周期一次额外 miss
  （192K 量级，频率低），对命中率影响 <1 个百分点，含在上述估算余量内。
- 推进阈值权衡（F 越小绝对成本越低、命中率略降）：96K ≈ 94% / $59；**128K ≈
  95.5% / $89（定案）**；160K ≈ 96.4% / $124。用户裁决统一参数、不做跑分
  特化；若后续实测命中率低于 90% 目标可再微调（可配 `ORZ_FOLD_TRIGGER_TOKENS`）。

## 6. 测试计划（实施时）

1. 推进幂等：推进后连续 N 个请求视图 = 前一视图 + 追加（字节级断言）；
2. 触发边界：估算 < 阈值不推进、≥ 阈值推进；无完整轮不推进；
3. 压缩联动：压缩后 fold 三态重置、旧台账入存档、marker 单滚动；
4. 前缀稳定性：长会话（≥10 轮）相邻请求视图差异 = 仅追加；
5. 恢复：恢复后 fold=None、重新累积；恢复预检截断不破坏；
6. 摘要输入与主请求同源一致性。

## 8. 风险与缓解

- 推进时一次全量 miss（窗口 128K 量级）：接受；每窗口一次，窗口内命中补齐，
  成本估算见 §5；绝对成本比 64K 推进方案高（$89 vs $33/窗口），但每轮成本
  仍为现状 1/4，且命中率更高（95.5% vs 91%）。
- 冻结台账块增长：每次推进增行有限；压缩时归档进存档，`messages` 只留
  marker。
- 与现有压缩触发测量（实测）与折叠推进测量（估算）口径并存：文档写明，
  实施时在配置注释与审计中标注。
- `build_collapsed_request` 既有调用点（主请求 + 摘要输入）全部迁移到有状态
  视图，避免两套口径漂移。
- 折叠推进无事件留痕（2026-08-18 审查收口已补）：每窗口一次前缀重写无法经
  `request_header_change`（只跟踪 system/tools/config）归因——新增
  `ledger_fold_advance` 事件（§3.3），实机验证按事件 + provider 缓存统计
  分窗口核对。
- 中途不完整轮（折叠边界内的轮次缺结果）可能被折叠成 `no_result` 行且声明
  从模型视图消失（2026-08-18 审查收口修复）：`collapsed_cut` 完整性回退
  改为覆盖**全部**将被折叠轮（`ranges[..collapse_count].all(is_round_complete)`），
  与「不完整轮保留原文」注释契约一致；正常流程不可达（结果在下一声明前必
  落盘），属防御加固。
