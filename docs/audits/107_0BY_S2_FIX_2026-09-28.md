## §1 修复内容

### 1.1 provision 落点（真因）

```powershell
# 修复前
$manifest = Join-Path $AcafRoot 'signer-manifest.json'
$keystore = Join-Path $AcafRoot 'keystore'
if (-not (Test-Path -LiteralPath $manifest)) {
    New-Item -ItemType Directory -Path $AcafRoot -Force | Out-Null
    & $provision $AcafRoot $manifest      # ← 落点错：建在 <acaf>，导出的是 <acaf>\keystore
}
# 修复后
if (-not (Test-Path -LiteralPath $manifest)) {
    New-Item -ItemType Directory -Path $keystore -Force | Out-Null
    & $provision $keystore $manifest      # ← 落点＝导出根
}
```

三处口径（provision 落点／`ORZ_ACAF_KEYSTORE` 导出／manifest 路径）自此同指一套；
`$env:ORZ_ACAF_KEYSTORE = $keystore` **原样未动**。

### 1.2 装配门（把静默失败变成响亮失败）

```powershell
Assert-True (Test-Path -LiteralPath $keystore -PathType Container) `
    "ACAF 密钥库根不是目录：$keystore（provision 落点与导出根必须同指；0by S2）"
Assert-True (Test-Path -LiteralPath (Join-Path $keystore 'installation-key.json') -PathType Leaf) `
    "ACAF 密钥库缺 installation-key.json：$keystore（0by S2 装配门）"
$keyBlob = @('installation-key.dpapi', 'installation-key.bin') | …（至少一件在册）
```

位置＝provision 之后、env 装配之前：这里正是本缺陷唯一的藏身处（装配不对 ⇒ 签名器 fail-closed
启动即退 ⇒ 客户端只看到「管道被关闭」⇒ 每条票据 `signer_unreachable`）。

### 1.3 装配清单补行

`dogfood_launch.ps1` 打出 `acaf = keystore=<…> / manifest=<…>`——被打出来的量才谈得上被核对。

### 1.4 同类面：`orz_acp_launch.ps1` 同病同修

该脚本与狗粮启动器**同形**（同样的 `$keystore = <AcafRoot>\keystore` 导出 ＋ 同样的
`& $provision $AcafRoot $manifest` 落点），故同批纠正并补同门；钉子对两枚脚本各跑一遍。

## §2 口径依据：为什么是 `<acaf>\keystore`（内层）

四处**互相独立**的来源同指一个口径：

| 来源 | 证据 |
|---|---|
| 容器/生产评测车道 | `tb_agents/orz.py`：`_ACAF_KEYSTORE_PATH = "/etc/orz-acaf/keystore"`／`_ACAF_MANIFEST_PATH = "/etc/orz-acaf/signer-manifest.json"` |
| 载体重建批（操作权威） | [`100 档 §3`](100_CARRIER_REBUILD_V081_DUAL_PLATFORM_2026-09-27.md)「`orz-acaf-provision <keystore> <manifest>`…keystore 两件哈希逐位未动（`f37556ab…`／`2aa80cb8…`）」＝内层那对；[`075 档`](075_CARRIER_REBUILD_DUAL_PLATFORM_2026-09-25.md) 同款命令并同时列出内外两对 |
| 历年实跑命令 | [`052 档`](052_CARRIER_REBUILD_AND_0AI_RELEASE_2026-09-16.md)／[`0AM 档`](0AM_DOGFOOD_CLOSURE_2026-09-17.md)：`ORZ_ACAF_KEYSTORE=…\acaf\keystore` |
| 两个启动器的导出值 | [`dogfood_launch.ps1`](../../scripts/dogfood_launch.ps1)／[`orz_acp_launch.ps1`](../../scripts/orz_acp_launch.ps1)：`$env:ORZ_ACAF_KEYSTORE = $keystore`（＝`<AcafRoot>\keystore`） |

反面的两处「外层」用法（[`orz_acaf_run.ps1`](../../scripts/orz_acaf_run.ps1) 的 `$Root` 一物两用、
[`s4_vm_acaf_reprovision.ps1`](../../scripts/s4_vm_acaf_reprovision.ps1) 的 VM 机器级 env）
都是**自洽**的（provision 落点与导出同值），属另一套独立部署，不构成本处口径依据。

**结论**：`dogfood_launch.ps1` 与 `orz_acp_launch.ps1` 的**导出值本来就是对的**，错的是它们
同一段里的 provision 调用——这也解释了为什么长期在役目录「看起来没事」（`<acaf>\keystore\` 一直在册，
且正是重建批每次核对四值的那一对），而**新目录**必然全灭。

## §3 方向更正（同批内，如实记）

| 序 | 动作 | 结果 | 状态 |
|---|---|---|---|
| ① | 首次落笔：改**导出值**为 `$AcafRoot` | 红 `RUN-CLI-6ab94e86` → 绿 `RUN-CLI-6ab94f1e`（新目录 26 事件／2 issued→2 consumed）＋在役 `RUN-CLI-6ab94fae` 绿 | **作废**（口径依据 §2 推翻该方向） |
| ② | 复核口径后改正：改 **provision 落点**，导出值复原 | 钉子红→绿；新目录 `RUN-CLI-6ab9513b` 绿；在役 `RUN-CLI-6ab95149` 绿 | **现行** |

作废理由（不是「跑不通」而是「不该这么修」）：① 会让启动器改读**另一枚**密钥库（在役目录里
外层那对是 2026-09-21 的另一套），② 与容器车道惯用路径 `/etc/orz-acaf/keystore` 不同形，
③ 与载体重建批维护的那一对分叉——**下一次重建刷新内层、而启动器读外层**，正是本立项要消灭的
「两处口径各说各话」。故①的两条读数只作过程记录，**不得**当作 S2 的绿证据引用。

   （S1 落的观测旁路仍在工作树里未提交，待 S3 随载体重建进体）。

   是**自洽的另一套部署**，本批不动、不统一——若日后要统一，须单独立项（会改 VM 与 harbor 透传面）。
3. **密钥库文件**：在役目录同时存在外层（`acaf\installation-key.*`，2026-09-21）与内层
   （`acaf\keystore\installation-key.*`，被重建批核对）两对；修复后**在役读取的是内层**（＝修复前一致），
   外层对当前入口已无引用。是否清理外层留用户裁决（本批只登记）。**内层不是遗留物**——它是正典。
4. **S3/S4 未做**：S3＝观测旁路随下一载体重建进体（并提交 orz 子树）；S4＝桌面零拒绝
   （本批两条绿读数即桌面单工具面）＋**容器形态回归零拒绝**（待跑）。
5. **未观测面**：签名器失败原因在**缺省**配置下仍不进 journal（需显式开
   `ORZ_ACAF_SIGNER_STDERR_LOG`）；「缺省也把首条 stderr 带进 `signer_unreachable` 的 detail」
   属可选强化，本批不动（候选，不占计数）。
