## 4. F3：检索面仍无产出，且**根因不可复核**

### 4.1 已排除与已坐实

- **不是抽取竞态（已排除）**：时序探针实测同一 Bing URL 在 **load 时刻** DOM 里已有
  `#b_results` ×1、`li.b_algo` **×10**、无 challenge，标题形态正常
  （`… - Search`）。即 orz 的选择器在 load 时点必然命中。
  （探针 A/B/C 三变体一致：10 条有机结果。）
- **不是抽取选择器不匹配（已排除）**：`ol#b_results` 直接子元素即 `li.b_algo`，
  与 `EXPR_SEARCH_BING` 的 `#b_results > li.b_algo` 一致。
- **Google / DDG 没有留下任何提交成功的导航**：Chrome History 里
  **没有任何 google.com 或 duckduckgo.com 记录**，而 Bing 记录在案。
  URL gate 是「形态门 + DNS + SSRF、fail-closed」，`www.google.com` 在本环境
  解析被污染成 `2001::1`，与 `blocked` 类（唯一来源 `CdpError::UrlGate`）吻合。
  边界：History 只记**提交成功**的导航，因此「被门拦」与「导航失败」两种成因
  在这一条上不可区分（两者分别落到 `blocked` / `timeout`，而精确 class
  同样受 §4.3 限制不可复核）。**DDG 有更强的直接证据**：模型侧记录 seq=431
  的 navigate 收到明确的「URL 策略拒绝」文案，属门拦。
- **Bing 导航确实发生、并被 302 到 `cn.bing.com`（已坐实）**：History 同时留下
  `www.bing.com/search?...&setmkt=en-US…` 与 `cn.bing.com/search?…` 两条。
  即 `setmkt=en-US` 在 URL 上（判据 6 成立）但**不阻止区域重定向**。
- **通用出口是通的**：同会话 `web_fetch` 成功取回 PLOS 全文（86KB）与 Addgene 博客，
  `web_fetch` 15 次 wall_avg 2,621ms。问题只在「搜索引擎」这一层。

### 4.2 形态：会话级失败备忘把整条链短路

- 首次 search（seq=108）耗 **44.7s** 且产生真实 Bing 导航 —— 链条跑满了一轮。
- 其后 3 次 search 只耗 **1,673 / 3,944 / 907 ms**，且 Chrome History **零新增导航**。
  代码面：`available_engines()` 会剔除会话内已备忘失败的引擎，且 `blocked`
  类**同样入备忘**（`serp.rs` 注释：Not a network failure but still memoized）。
- 结论：首次一轮里三个引擎都被记为失败并备忘，之后每次 search 直接
  `all_engines_failed` 返回 —— 机制按设计工作，但**一次瞬时首败即整会话失去检索引擎**。

### 4.3 缺口：引擎级结果没有任何持久化面（**本批最重要的框架发现**）

- `events.jsonl` 全卷无 `engine_attempts` / `error_class` / `low_quality` / `serp` 字样
  —— 事件面按设计只落 `ToolCompleted` 事实。
- 唯一一次 Bing 导航**到底抽到没有、落在哪个 class**，只存在于交给模型的
  工具结果文本里；该文本既不入 journal，也不入 `.gsa` 卷（卷内只有
  `events.jsonl`、`ledger/current.md`、`retrieval-results/*.json`、Chrome profile），
  `agent/trajectory.json` 仅含模型侧消息、不含工具结果。
- 因此 **0v 判据 1/5/7 在设计上不可事后取证**：机制可能完全正常，验证面却拿不到
  证据。这与判据原文要求的字段（`engine_attempts.error_class`、`low_quality` 标注）
  直接冲突。**建议按独立设计项处理（见 §6）。**

### 4.4 顺带发现（登记备查）

- **Chrome History 读取装置有坑**：分析器报 `no such table: urls`——`History`
  本体仅 4,096 B、数据在 1.1 MB 的 `History-wal` 里；必须**连同 `-wal`/`-shm`
  一起复制**才能读（本批用 `read-chrome-history.py` 完成）。
- **`web_search` 原生通道整场退化**：模型记录 4 个查询全部返回空结果
  （与 0u/R4「服务端尾毛刺」同族，属环境侧）。
- **`search` 与 `navigate` 的分工露出**：模型在 search 无效后改走显式
  `navigate` 到 `www.bing.com/search` / `cn.bing.com/search`（seq 547/570），
  两次仅 795/707 ms 且 History 有记录 —— 说明 URL gate 对 Bing **是放行的**。
  这条反证进一步支持 §4.3：Bing 那一次失败发生在**导航之后**。

## 6. 建议的下一步（待用户裁决）

1. **补引擎级取证面**（框架侧，通用价值最高）：让 `browser_control search`
  的 `engine_attempts`（引擎 / class / 耗时 / 是否备忘）与 `low_quality` 标注
  **落进可事后复核的面**（事件面扩展或会话卷落盘）。没有这一步，判据 1/5/7
  永远只能靠模型的自然语言声明。
2. **定向探针**（装置侧，不须改 orz）：同容器、固定查询集、显式多次引擎导航，
  一次取证判据 1/5/7 与 9/10。
3. **F3-h1 待判**：首败即整会话备忘是否过严（本例中 Bing 唯一一次导航后
  即被标记失败并永久移除）——是否需要一个「失败不跨查询固化」或
  「重试窗口」语义，属设计问题，待用户裁决。
