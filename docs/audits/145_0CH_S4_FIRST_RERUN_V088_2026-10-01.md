## §4 S4 判读二：新露「第三摩擦」与定因（已裁：0ch 已接受边界）

**现象**：apt 装 git/openssh-server 时 `libcryptsetup12 2:2.7.0-1ubuntu4.2` 解包失败——

```text
dpkg: error processing archive .../libcryptsetup12_2%3a2.7.0-1ubuntu4.2_amd64.deb (--unpack):
 unable to install new version of './lib': Permission denied
dpkg-deb: error: paste subprocess was killed by signal (Broken pipe)
```

**定因（差分测试）**：同镜像、不经 orz 守卫，`docker run … apt-get update && apt-get install -y libcryptsetup12`
**rc=0 干净通过**（Setting up / Processing triggers 全链正常）⇒ 镜像与 Ubuntu 软件源健康，
拒绝来自 **orz L3 Landlock 守卫侧**。

**机制**：该镜像 `/lib -> usr/lib` 为**根级符号链接**（usrmerge 形态）；dpkg 解包需替换/备份该
根级条目（rename 到 `*.dpkg-*`），需要 `/` 本体上的 **REMOVE/rename 权**——0ch 设计明文排除
（`ROOT_MAKE_GRANT` 恰 5 位 make 子集，REMOVE_*/WRITE_FILE/TRUNCATE 绝不上 `/`：union 语义下
即扬盘保底失守；根级删除恰是规则 1 的威胁模型本体）。

**三点定性**：

1. **不是 0ch 引入的回归**——0.8.7 对 `/` 更严（连 make 都无）同样拒；rerun3 卷中零
   `libcryptsetup` 痕迹＝当时 apt 先死在 `/dev/null` 写拒上、根本走不到解包步。0.8.8 放行
   apt 自身后，问题才**首次到达**此墙。
2. **不宣放行**——给 `/` 加 REMOVE 即拆掉防删除保底本体；**用户裁决＝作为 0ch 已接受边界
   注记（已知代价），不立项、不放行**。
3. **模型本有绕行面（未尝试）**——`openssh-server` 才是 systemd→libcryptsetup12 依赖链的
   源头，`--no-install-recommends git nginx` 瘦装极可能整链绕开（git 本体不依赖 systemd）；
   或 `dpkg-deb -x` 手工侧解包落 `/usr`（baseline 授权面内）。模型修 dpkg 未果后未走瘦装。

**如实记（模型行为面，与 0ch 修复不矛盾）**：本次判 0 的直接形态已从「写摩擦死亡螺旋」变为
「apt 环境墙＋**检索偏航**」——dpkg 修复未果后模型转向上网查题面规范（浏览器车道不可用走
fetch 车道；发现 terminal-bench 上游仓库已改名 `harbor-framework`、api.github.com 逐字规范
未取得），并翻查 `/logs/verifier`，把剩余分钟烧尽于检索兔子洞。

**杂项核销**：`/zlink_at_root` 为**模型自身** rename 探针残留（`ln -s usr/bin /zlink_at_root`
make 成功〔0.8.8 放行面的正确行为〕→ `rename` 被拒〔保底正确行为〕），非框架残留物。
