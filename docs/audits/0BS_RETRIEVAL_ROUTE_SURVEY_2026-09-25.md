# 0bs 检索线路线调研：无代理直连实测与现成方案体检（2026-09-25）

- 日期：2026-09-25
- 性质：**只读调研＋实测读数**（零产品代码改动）；落账去向＝`0bs` 内件 ⑩⑪⑫（用户令「检索部分的处理也并进 0bs 好了」）
- 触发：用户令「当前的 http 直连脚本形式在无网络环境的情况下基本只能百度，但百度很差，会影响模型的信息获取质量，github 上有没有相关解决方案？自己做反爬太麻烦了」＋追问「直连都能成功读数吗？之前的测试里多次返回反爬的结果」
- 证据脚本：仓根 `.tmp-retrieval-impersonate-probe.py`（curl_cffi 0.16.3 双态对照；`.tmp-` 前缀属门禁忽略面、不入库）；环境＝本机 Windows，**强制直连**（`--noproxy '*'`／`proxies={"all": ""}`，本机系统代理为 `127.0.0.1:7890` 已刻意绕开）

## 1. 一句话结论

「HTTP 200 ＋ 有字节数」**不等于拿到可用读数**：直连下五个中文可及引擎呈**三态**——① 风控拦截（百度、搜狗：无指纹伪装时只有 1.4–5.4 KB 验证/拦截页）；② 有结果但被降级（Bing CN：长技术查询返回泛化热门站）；③ 有可用结果（360、以及**加上 Chrome 指纹伪装后的百度与搜狗**）。**TLS/HTTP2 指纹伪装是必需项**（同 URL 同版本客户端，仅换 `impersonate` 就从拦截页变 900 KB 真结果页），而**元搜索自托管与指纹伪装在 SearXNG 里本就是同一件事**（其网络层即 curl_cffi，`DEFAULT_IMPERSONATE = "chrome"`）。

## 4. 裁决（用户令 2026-09-25）与形态

### 4.0 追加裁决（同日第二令）：HTTP＝兜底，主战场＝本地浏览器车道

- 用户令：「http 本身终究还是兜底，实际上主要还是优化本地浏览器车道，有真机浏览器的话就安全和方便不少，关键是要让模型能够正常使用浏览器」。
- **360（及各家）清洗件的体检结论**：GitHub 上**没有可用的独立 360 清洗项目**（仓库检索仅命中 2016 年的 `cl3403/360SerpScraper`，0★、11 年未动）；**现成清洗面在 SearXNG 单仓内**——`searx/engines/`：`360search.py` 114 行（`li.res-list` ＋ `h3.res-title > a[data-mdurl|href]` ＋ `p.res-desc`／`span.res-list-summary`）、`baidu.py` 219 行、`sogou.py` 141 行、`quark.py` 382 行、`bing.py` 189 行，全部上游持续维护 ⇒ **「不自写清洗」的落点就是把它当清洗源用**（可整体自托管，或按需移植其选择器并保留来源标注）。
- **车道定位（本档 §4 项 1、2 的层级修正）**：HTTP 检索路线（SearXNG＋指纹伪装）**降为兜底**；**本地浏览器车道＝主战场**，判据＝**模型能正常使用浏览器**。相关实测支持＝浏览器车道可靠性依赖「真机＋有头」（技能侧：真机有头 4/4 相关 vs headless 0/5；且**沙箱内**同一调用返回无关降级页、**沙箱外**返回真 SERP ⇒ 浏览器车道与沙箱面的关系须显式设计）。

1. **HTTP 检索线＝「元搜索自托管 ＋ TLS/HTTPS 伪装」混合（有必要，但不是两套解析）**：
   - **聚合层**＝自托管 **SearXNG**（JSON API 单一入口；引擎集裁到直连可达者；**指纹伪装随其网络层自带**）；
   - **传输层**＝指纹伪装**只在无 sidecar 兜底与 `web_fetch` 抓页时需要**（Rust 侧 `wreq`／sidecar `curl_cffi`；本机实证：百度/搜狗无伪装即拦截）；
   - **不做**：不自己写引擎解析与反爬（现行 `local_segmented` 已承担百度/搜狗/360 各自解析＋跳转解包＋相关性闸门，维护成本已实证偏高）；
   - **已知不可用**：夸克（阿里 `tmd/punish` 风控，指纹无效）——除非交给浏览器车道。
2. **本地检索路径底座＝反检测浏览器**（用户令「反检测浏览器这步值得做，加给本地检索路径」）：`camoufox`／`DrissionPage`／`nodriver`／`patchright` 择一作为 `local_browser` 通道底座（与 0bp B 路径共用选型）。
3. **检索源补充＝加**（用户令「检索源补充值得加」）：直连友好的高质量垂直源（GitHub／Stack Exchange／arXiv／OpenAlex／Crossref／PyPI／npm）纳入检索源面。

### 4.4 第二令修正（2026-09-25）：HTTP＝自建小集＋只做伪装；浏览器车道＝真机

- 用户令：「浏览器车道肯定走真机环境啊，orz 自己都不在沙箱里面了」／「orz 跟着上游更新也不是个事，360 既然是怎么都可达且可用，那我们就只做伪装，http 层留 DDG/bing（非 cn bing）/百度/360，这样就不用跟着上游更新了，子代理好歹也是和主代理同级的模型，对结果的判断就交给他了」／「剩下的就是本地浏览器的指纹伪装＋我们自己做的检索动作伪装」。
- **HTTP 面（⑩）定稿**：自建四引擎小集 **`duckduckgo`／`bing_global`／`baidu`／`360search`** ＋ **只做 TLS/HTTP2 指纹伪装**；**不引入 SearXNG 运行时依赖、不跟上游更新**——SearXNG 的 `360search.py`（114 行）等**只作移植参考**并留来源标注（原 §4.1 的「聚合层＝自托管 SearXNG」作废）。**结果质量判断交检索子代理**（与主代理同级模型），机械层只取回与如实回传。
- **浏览器车道（⑪）定稿**：环境＝**真机、无沙箱**（与生产面口径一致：orz 自身不在沙箱内，故沙箱适配不再是设计项）；**指纹面天然为真**——真机已装浏览器＋真实 profile ⇒ 不需要 camoufox 类反检测底座，接入＝CDP 接真机浏览器／复制登录态 profile 避免锁／有头优先／避免自动化痕迹（不启用 `--enable-automation`）；**自研检索动作伪装**＝已落 pacing＋jitter（`local_browser/serp.rs`：session pacing ≥5 s＋0–50% jitter），设计已定人化输入（逐字符键入＋提交前停顿＋Enter）但**当前不可达**——`local_browser` 的 CDP 白名单明确禁 `Input.*`／`Runtime.*` ⇒ 需 S1 设计门放开最小输入动作集（键入／回车／滚动／点击）＋节奏伪装，并同步定 URL 门禁与审批边界。
- **同批补测读数（强制直连，curl_cffi 0.16.3 双态）**：百度 无伪装 1,438 B／验证页 → Chrome 指纹 **745,746 B／118 结果标记**；360 两态均 ~358 KB／7 结果（无风控）；**Bing 家族两态都降级**——`bing_cn` 与 `bing_global` 同返「Rust 程序设计语言／Rust Programming Language／菜鸟教程」泛化标题（⇒ **换非 cn Bing 不解决降级**，降级属 Bing 对该出口的行为，最终仍须靠浏览器车道或代理拿真 SERP）；DDG 直连不可达（需代理）；夸克指纹无效、不进集。

### 4.5 第三令修正（2026-09-25）：Bing 出集、CDP 直连真机不复制、动作面放开＋输入拟真常驻

- 用户令：「那 http 层的 bing 也不留了」／「CDP 直接直连用户真机浏览器，直接启动即可，不复制，当前浏览器占用的话，模型自己看浏览器控制栏进行判断，如果用户在明确使用浏览器，那就启动无头；如果只是进程挂着，那就直接用当前进程」／「模型对浏览器的使用是完全的，和用户一样，在具体使用上不做限制」／「输入动作方面，常驻，由机械层直接机械做，模型下发指令后机械层自动做对应的输入动作拟真，避免拦截和风控」。
- **HTTP 集（⑩）＝三件**：`duckduckgo`／`baidu`／`360search`；**Bing 家族整体移除**（依据＝§4.4 实读：`bing_cn` 与 `bing_global` 两态皆降级）。DDG 直连不可达 ⇒ 定位为**有代理时的质量源**；本体仍只做 TLS/HTTP2 指纹伪装。
- **接入形态（⑪）＝CDP 直连用户真机浏览器，orz 直接启动，不复制 profile**（取代「复制登录态 profile 避免锁」的先前措辞）。
- **占用判定交模型**：机械层给出浏览器状态事实（控制栏／占用态），模型自行判断两分支——**用户明确在用 ⇒ 启动无头实例**；**仅进程挂着 ⇒ 直接用当前进程**。
- **动作面＝用户等价、不设使用限制**：取消现行 CDP 白名单对 `Input.*`／`Runtime.*` 的限制（标签页、下载、脚本等一并不设动作级限制）——即「模型对浏览器的使用是完全的，和用户一样」。
- **输入动作伪装＝常驻、机械层自动施加**：模型下发指令后，机械层自动做对应输入拟真（键入／停顿／滚动／点击节奏），模型无感；目的＝避免拦截与风控（现行 `local_browser/serp.rs` 的 pacing＋jitter 是这一面的前身）。
- **S1 待定（本令的连带面，须一并定口径）**：① 动作面放开后「UI 零执行事实」与 URL 门禁／审批面的重新表述（浏览器内脚本/下载可产生外部效果，与既有边界需要对齐）；② 占用判定所需的事实形状（控制栏读数的机械来源与事件面）；③ 无头实例与真机实例的会话隔离与并发 1 语义；④ 拟真参数（间隔分布、停顿、轨迹）的单一源与可核性。

### 4.6 第四令（2026-09-25）：S1 四项结清＋输入拟真的可引用数据源

- 用户令：「动作放开就行……下载和脚本执行的话一律弹验证，需要用户明确批准才能执行」／「无头和用户实例两端不混用，单次子代理进程中只使用一类，每次使用时对所使用的浏览器类型进行记录留档即可」／「占用判定的话……模型直接查看当前浏览器页面的占用和活跃情况以及界面内容/操控情况就好了」／「拟真参数的话，就统一定一套固定标准即可，有没有能查的相关数据用来确定人类的平均操作数据？」。
- **结清口径**：① 动作面全面放开，**唯二门禁＝下载与脚本执行**（弹验证＋用户明确批准）；② 无头／用户实例**不混用**（单次子代理进程只用一类）＋**每次记录所用浏览器类型留档**；③ 占用判定**不另设机械事实面**（控制面已对模型开放）；④ 输入拟真＝**统一固定标准、单一源**。
