# 106 0by S1 勘定：ACAF 签名器不可达（桌面形态）根因定位（2026-09-28）

> **日期**：2026-09-28；**用户令**：「请进行0by S1部分吧」。
> **本批＝S1 勘定批**（根因成立＋变量隔离＋补观测缺口）＋ **orz 源码面观测旁路落码**；
> 计数 **55 不变**（`0by` 维持 `pending`，闭合留 S2–S4）；**未提交／未推送**。
> **本批改判**：104 批「0.8.1 相对 0.8.0 无已知代码变更可解释差异」的推论**被否**——
> 差异**不在载体版本**，而在 **launcher 面**（新 bin 目录下密钥库根拼错一层）。

## §0 结论速览

| 面 | 结果 |
|---|---|
| **真因** | `scripts/dogfood_launch.ps1` 把密钥库根算成 `<AcafRoot>\keystore`（并据此导出 `ORZ_ACAF_KEYSTORE`），而**同一脚本**的 provision 调用把密钥库建在 `<AcafRoot>` —— 两者错开一层目录 |
| **失效链** | 新 bin 目录 ⇒ manifest 不在册 ⇒ 现场 provision 建成 `<acaf>\` ⇒ orz 被指向不存在的 `<acaf>\keystore` ⇒ 签名器**启动即退**（exit 1）⇒ 客户端只看到管道被关 ⇒ 每次签票 `signer_unreachable` ⇒ **票据类工具面全灭** |
| **「0.8.1 未复现」的真解释** | 该轮用的是长期在役目录 `D:\tb-eval\orz-windows`，其中 `acaf\keystore\`（2026-09-12 14:33 遗留）**恰好**让错路径解析成功 —— 纯属偶然，与版本无关 |
| **载体版本轴** | **排除**：0.8.0／0.8.1 两枚签名器在**正确根**下都 exit 0 且正常应答；在**错误根**下都 exit 1 |
| **容器形态零拒绝** | 与桌面不同源：容器侧密钥库经另一条 provision 路径落位，不存在本处路径错配 |
| **观测缺口** | 已补（本批落码）：`ORZ_ACAF_SIGNER_STDERR_LOG` 可开闭旁路，缺省行为逐字节不变 |
| **判定** | S1 三件（最小复现／变量隔离／补观测缺口）**达成**；`0by` 维持 `pending`，**计数 55 不变** |

## §1 真因：秒级复现（红证据）

### 1.1 启动器等价复现

入口：[`probe_acaf_keystore_root.py --emulate-launcher`](../../scripts/probe_acaf_keystore_root.py)（本批新增，登记于
[`scripts/LIFECYCLE.md`](../../scripts/LIFECYCLE.md) `retained` 面）——在空目录上照 `dogfood_launch.ps1` 的 ACAF
装配顺序重放（缺 manifest ⇒ 现场 provision ⇒ 导出 `<acaf>\keystore`），只换密钥库根一个变量：

```text
载体三件套已从 D:\tb-eval\orz-windows 复制到 <scratch>\bin（照新 bin 目录形态）
provision exit=0
provision 生成：['installation-key.dpapi', 'installation-key.json', 'signer-manifest.json']
[启动器装配] ORZ_ACAF_KEYSTORE=<scratch>\acaf\keystore
      exit=1  红（密钥库根不可用：目录不存在）
      stderr=orz-signer fatal: keystore error: installation key root is not a directory: <scratch>\acaf\keystore
[根改为 provision 位置] ORZ_ACAF_KEYSTORE=<scratch>\acaf
      exit=0  绿（密钥库可加载，签名器应答）
      stderr=(空)

红证据成立=True（红：启动器装配下签名器启动即退；绿：同一二进制换根即应答）
```

**读法**：provision 自报的 `launch env:` 行写的是 `ORZ_ACAF_KEYSTORE=<AcafRoot>`（provision 自己的口径），
而启动器随后导出的是 `<AcafRoot>\keystore` —— 两个「权威」在同一脚本内自相矛盾，错的那一个才下了沉。

### 1.2 六格变量隔离矩阵（载体 × 密钥库根）

```text
绿  orz-windows        exists=True  provision 实际位置 <acaf>
绿  orz-windows        exists=True  启动器实际导出 <acaf>\keystore   ← 2026-09-12 遗留目录把它救活
绿  orz-windows-080    exists=True  provision 实际位置 <acaf>
红  orz-windows-080    exists=False 启动器实际导出 <acaf>\keystore
绿  orz-windows-080c   exists=True  provision 实际位置 <acaf>
红  orz-windows-080c   exists=False 启动器实际导出 <acaf>\keystore
```

| 载体目录 | 签名器版本 | 密钥库根＝provision 位置 | 密钥库根＝启动器导出 |
|---|---|---|---|
| `D:\tb-eval\orz-windows`（长期在役） | 0.8.1 | **绿** | **绿**（遗留 `acaf\keystore\` 在册） |
| `D:\tb-eval\orz-windows-080` | 0.8.0 | **绿** | **红**（`installation key root is not a directory`） |
| `D:\tb-eval\orz-windows-080c` | 0.8.1 | **绿** | **红**（同左） |

**推论**：

1. **载体版本轴排除**——两枚签名器对同一个「根」给出同一个判定，0.8.0／0.8.1 之间无差异。
2. **launcher 面轴成立**——翻转只在「密钥库根」这一格发生。
3. 104 批三条排除实验（长期库／新建库／新建库＋0.8.1 签名器全应答）**结论仍成立**，但其
   [`.tmp-b104-acaf-probe.py`](../../.tmp-b104-acaf-probe.py) 把 `ORZ_SIGNER_KEYSTORE_ROOT` 指向
   `<acaf>`（**provision 的真实位置**），恰好绕过了错配——当时那条探针因此不可能发现本缺陷。

### 1.3 长期目录为何「救活」了 0.8.1 那轮

- `D:\tb-eval\orz-windows\acaf\` 同时存在两套密钥库：外层 `installation-key.{json,dpapi}`（provision 产物）
  与内层 `keystore\installation-key.{json,dpapi}`（**2026-09-12 14:33** 遗留）。
- 0.8.1 桌面轮 `RUN-CLI-6ab9363d` 用的是该目录 ⇒ 错路径 `<acaf>\keystore` 解析到遗留内层 ⇒ 签名器正常启动
  ⇒ 18 张票据全 issued→consumed、零拒绝。
- 0.8.0 两轮 `RUN-CLI-6ab93831`／`RUN-CLI-6ab93aaa` 用的是**新目录**（`-080` 建于 23:36:55、`-080c` 建于
  23:47:53，`acaf\` 内只有三件 provision 产物、**无 `keystore` 子目录**）⇒ 错路径落空 ⇒ 票据类工具面全灭。
  ⇒ **两批之间的「差异」是目录形态，不是版本**。

## §5 边界（如实记）

1. **本批不改启动器**：S1 只勘定与补观测面；`dogfood_launch.ps1` 的密钥库根错配**仍未修**（S2 范围）。**【2026-09-28 勘误】该错配已随 S2 修复**——修的是**同一段里的 provision 落点**（`& $provision $keystore $manifest`），**`$keystore` 导出值原样未动**；另：在役目录的`acaf\keystore\` **不是遗留物而是正典**（容器侧 `/etc/orz-acaf/keystore`、载体重建批 provision 落点、历年实跑命令四处同指），本档 §0／§1.3／§5 中「遗留内层」「密钥库根拼错一层」的措辞据此更正。见 [`107 S2 修复档 §2/§3`](107_0BY_S2_FIX_2026-09-28.md)。
   为做 A/B 而在绿侧手工造出的 `acaf\keystore` 属**诊断装置**，不是修复。
2. **诊断载体非发布件**：本批的 orz 改动止于源码面（**未 bump、未重建 release、未进包、未发行**）；
   S3 才把旁路随下一载体重建进体。
3. **轴覆盖边界**：「负载」一格按**不适用**记——首调用即全灭、与并发／负载无关（红侧 3 次尝试每次都停在同一
   失败点）；「ACAF 件」轴由三个载体目录（长期库／新建库×2）天然覆盖；launcher 面的「直起 orz／经 Tee 管道」
   子轴**未单独走**，因为 Tee 只作用于 orz 的 stdout 捕获链，而真因是**启动环境变量里的路径**（签名器另有
   独立 stdin/stdout 管道），两者不相交。
4. **作用面**：本缺陷只影响**经 `dogfood_launch.ps1` 装配的新 bin 目录**；容器形态与
   [`orz_acaf_run.ps1`](../../scripts/orz_acaf_run.ps1)（该脚本 `$Root` 同时作密钥库根与 manifest 根，自洽）
   不受影响。
5. **0.8.0 对照载体**（`D:\tb-eval\orz-windows-080`／`-080c`）与桌面三轮卷仍留档；本批新增
   `D:\tb-eval\orz-dbg106-red`／`-dbg106-green`／`tmp\b106-launcher-emul` 三处诊断装置留在原处待裁决。
