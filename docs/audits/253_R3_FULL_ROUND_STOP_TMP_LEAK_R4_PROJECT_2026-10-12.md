## §3 /tmp 指令泄漏通道（本轮核心发现）

- **通道**：适配器（`orz_multistep.py`）每 checkpoint 上传题面指令至 `/tmp/orz-instruction-{N}.md`（「长指令走文件不走 argv」），容器内 driver 读取后**从不清除**→ 前档指令逐档堆积可读。
- **实证**：p04 ck3 journal 记录模型执行 `cat /tmp/orz-instruction-1.md /tmp/orz-instruction-2.md`（读前两档指令后继续工作）；全扫 **14/14 题**、150 处读取事件命中该通道。
- **定性**：与 0cw 跨对话污染**同类**——会话限域数据（harness→agent 的本档通信）存活到后续会话可读空间；差异在写入者：0cw 是 orz 自身会话数据面失守（0cy 已治本），本次是 **orz 之外的宿主件**在 0cy 卫生域（.gsa）之外写入——**清扫机制管不到域外写入**。
- **治理规则（本批立为设计纪律）**：会话卫生完备条件＝清扫机制（0cy，已建）**＋写入面纪律**——会话限域数据要么写进 `.gsa`（进卫生域）要么用后即焚；禁止落在域外持久位置。**非 prompt 式接入/交接（文件、sidecar、状态文件）若不即焚，结构性遇到本泄漏**；prompt 通道天然会话限域。
- **影响面**：r3 与 0cw 同泄漏形态，二者 A/B 可比性成立；对论文严格重置口径，ck2+ 分数可能轻度系统性偏高——V4 报告显式登记此偏差。
- **修复（r4 S1，未实施）**：driver 读取后即删（或适配器上传前清旧 `rm -f /tmp/orz-instruction-*.md`）；一行级。

### /tmp 的四个角色（澄清）

| 角色 | 路径 | 定性 |
|---|---|---|
| 适配器指令交接 | `/tmp/orz-instruction-{N}.md` | **泄漏源**（应即焚而未焚） |
| ACAF home | `/tmp/orz-home` | 机器面配置，跨档持久＝设计内 |
| 连续形态 daemon 套接字 | `/tmp/orz-acpd-<hash>.sock` | 仅 0cr 形态用，r3 未触 |
| 模型自有工程沙箱 | `/tmp/dyn1`、`/tmp/ct3`… | 正常工程行为（灰色：前档痕迹可读，论文系 agent 同样存在） |

## §4 归因方法（轮末 V4 沿用）＋ dag_execution 完整样本
