# 284 批：任务级计费机械记录点立项（0df）——per-task metering 随会话存档（2026-10-16）

> 性质：**登记批**。零源码、零跑批、零 API 调用；本批只做立项登记与治理面同步，
> 计数 **61 → 62**。

## §1 由来

- 2026-10-16 Reddit 评论线第三轮：评论者对上一轮回复追问粒度——
  「session-level token counts anywhere, or only usage-page daily totals?」，
  并指出该问**决定单任务成本是直接归因还是只能按天倒推工作量**。
- 用户在回复中给出意向：**「我打算给下一个版本的 orz 配个任务级计费，跟着会话一起存档。」**
- 用户随即下令：**「请将这一内容记为待办吧，作为新的机械记录点。」**——本批即该项登记。

## §2 立项内容（0df · PER-TASK-METERING-RECORD-POINT）

| 维度 | 登记值（用户意向，细则未裁决） |
|---|---|
| 计量单位 | **任务**（run／题） |
| 计量内容 | token（`cache_hit`／`cache_miss`／`completion`）＋**真口径金额**（实付） |
| 记录形态 | **机械记录**——机械层记账、**不投递模型面**（沿 0bg `lif_domain` 先例） |
| 存档面 | **随会话存档同走**（与 0cy 会话卫生收卷／0dd 手动存档面接口） |

- 金额口径沿 283 批：实付与折算**两栏分列**，不得以折算值冒称实付。

## §3 动因对照（为什么需要机械记录）

- 283 批的单任务成功成本**全部是事后只读复算**：逐题余额差分（`r4_problem_ledger`）＋
  10 分钟粒度余额序列对齐，靠人手把金额落到题目粒度。
- 反例即 283 批的 TB 2.1 半边：该轮**金额面不可得**——`jobs-official` 210 份 `result.json`
  的 usage 字段逐件 null（适配器不上报）、该窗无余额台账、控制台分项未取回。
- ⇒ 同一 harness 同一模型，只因**缺机械记录**，一轮能给单任务成本、另一轮只能给 token 口径。
  本项即补齐该缺口：把「事后对齐」变成「记录自带」。

## §4 S1 待勘定（五项，均未裁决）

1. **kind 闭枚举扩档**：机械记录新 kind 需 schema＋Python 镜像＋Rust 三处同改
   （沿 0ae／0bg 纪律）。
2. **金额来源**：provider 账单侧读数 vs 宿主侧余额差分（前者准、后者自足）。
3. **粒度**：run 级汇总 vs 题级（SCB 形态下题＝一次 run，TB 形态下题与 job 对应关系须先勘定）。
4. **接口**：与会话存档包形态（0dd 手动存档／0cy 收卷）的挂接点。
5. **档位设计值**（2026-10-17 用户令追加）：把**配置侧的 reasoning effort 档位**写进任务行——
   与观测到的 reasoning token **分列**。实证：r4 轮全轮恒定一档，但观测推理 token 占 completion
   76%（逐题 28%–90%，200 份会话／14,363 次模型调用）⇒ 档位恒定不等于推理量恒定，两值都要有。
   **现状边界**：该轮 journal 只有 `reasoning_tokens`，无 `reasoning_effort`／`thinking` 等配置键——
   即"档位设计值"目前**无可回查来源**，只能在后续记录里补盖。

## §5 边界与不得宣称

1. 本项为**意向登记**：细则未裁决，实施顺序与批序未定；不得据本档宣称任何已实现能力。
2. **不动模型面投递**：机械记录只记不发（若需模型可见，另行立项）。
3. 本批**零源码、零跑批、零 API 调用**；`orz/` 子树未触碰。
4. 单任务数值的口径边界（k=1、成功样本极小、档级／题级分母、失败代价结构）沿 283 批 §7。
