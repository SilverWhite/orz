### 2.3 331：状态机方向对，公开状态 over-spec

331 的 owner/lease/close/删除不复活/有界/错误段设计是合理的，且「`SessionCommand` 传输无关、ACP 只是适配器」的方向符合 330 的「底座可更换」裁决。但设计本身有三处需要收敛：

1. **`closing` 与 `archived` 被写成公开状态，却没有可观测面**。`closing` 只存在于 close 调用内部的轮询窗口，而实现把「置 `closing=true`」与「从 sessions 表移除」放在同一临界区（`acp_server.rs:5060-5061`），任何 `session_state` 都读不到 `closing`；`archived` 在 `SessionState` 枚举里存在，但全仓没有构造点（§4.3）。设计若保留这两个状态，就必须有状态通知/查询/持久化；若不保留，应从公开状态机删除，避免「设计有七态、实现只有五态」的长期误差。
2. **「六动词」标签与 §3.2 的十一行动词表不符**。331 §3.2 实际列出 `new/load/attach/prompt/终态事件/cancel/close/archive/restore/delete/evict` 十一行；索引 `AUTH-0DK-SESSION-LIFECYCLE-DESIGN` 与 BACKLOG 却写「六动词」，且 TODO 写成「六动词状态机（created/idle/…）」把动词与状态混在一起。这是稳定 ID 定义层面的错误，会误导后续把 archive/restore 当成「不在状态机内」。
3. **单 owner 没有覆盖 archive/restore**。332 把 close/delete/evict 收进了 `session_ops`，但 archive/restore 仍走 0cy/CLI 路径，`SessionCommand` 定义了却从未使用（§4.3）。「一张表、一个 owner」的验收尚未成立。

### 2.4 332/333 的批次边界

332 的范围（close/有界/删除不复活/占用者提示/状态通知）与 333 的范围（Web 九细节）本身是合理的拆分；两批都不重建，符合训练进程约束。问题在于：

## §3 P0（0.9.8 门禁级／必须裁决）

### 3.1 版本偏斜检测结构上不可能命中（333 必闭第 8 条失效）

**事实**：
- `orz-web/src/lib.rs:50`：`agent_binary = std::env::current_exe()`；`lib.rs:115/123` 把它同时交给 `AgentBridge` 与 `ServerState.agent_binary`。
- `orz-web/src/server.rs:835-848`：`bridge_version` 由 `std::env::current_exe()` spawn `--version`，`child_version` 由 `state.agent_binary` spawn `--version`。
- 两者是**同一路径、同一文件、同一版本的两次调用**，因此 `version_skew` 在正常运行时恒为 `Some(false)`；只有两次 spawn 之间文件被替换才可能 `true`，而那时反而会误报。
- 典型目标场景（桥进程内存里是 0.9.7，磁盘已换 0.9.8，刷新后新 child 是 0.9.8）在此实现下**永远报不出偏斜**：两次探针都读磁盘新文件。

**影响**：333 §0 把「`--version`＋桥/child 版本偏斜横幅」列为必闭第 8 条已落；实际横幅只能在冒烟直接注入 `version_skew: true` 时出现（`frontend_smoke.mjs:1580-1594`），**没有生产触发路径**。这是 330 自己警告的「机制有了、不变量没落」的典型复发。

**建议**：`bridge_version` 改用编译期 `env!("CARGO_PKG_VERSION")`（桥进程真实在跑的版本），`child_version` 由 `--version` 或 ACP `initialize` 自报；给探针加超时（旧载体 `--version` 不存在时会落入裸 `orz` 的 TUI 分支，见 `orz-bin/src/main.rs:166` 与 `:412-417`），并补一条「两个不同版本 bin」的 boot 单测。另：每次 `/api/boot` 两次同步 `Command::output()` 在 async handler 内阻塞（`server.rs:812-822`），建议缓存或改异步。

### 3.3 CLI 删除绕过 close/lease，且墓碑先行（数据破坏面）

**事实**：
- `orz/crates/orz-bin/src/main.rs:986-988`：`orz delete-session` 直接调用 `delete_session_on_demand(&cwd, session8)`，**不经过** `SessionCommand::Delete`、不 close、不检查 lease、不检查是否有在途 run。
- `acp_server.rs:2410` 的 `delete_session_on_demand`：`2508-2522` 先 `if paths.is_empty()` 返回，再 `write_session_tombstone`，然后逐件删除，**首个删除失败即 `?` 返回**。
- 设计 §7（331 档）明确：「CLI `delete-session` 走同一 `SessionCommand::Delete` 原语（先 close，再删）；跨进程持 lease 时 `lease_conflict`。」实现与该条相反。
- 332 档 §5.4 已登记「Web 既有删除仍走 CLI 维护面（已写墓碑）」，但未登记「绕过 lease/close」这一偏差；333 也没有把 Web 删除改到 `_orz/session_delete`（`acp.js` 的 `sessionDelete` 无调用者）。

**影响**：
1. Web 探索器可删一个**另一个进程（TUI/`orz-codex`/`orz -p`）正在跑**的会话：删除侧车/journal 时在途 run 仍写 `.gsa/runs` 与 orientation/activation（`4378`/`4412` 无墓碑检查，只有 conversation 侧车 `1016` 有），可造成文件占用失败、半删、墓碑永久拒绝该会话（`prompt`/`load` 全 `not_found`）。
2. 部分删除失败后，`_orz/session_delete` 因 `is_deleted` 早退返回 `already=true`，不会继续删；只能靠 CLI 重试（CLI 不检查墓碑，可续删）——但用户看到的是「已删除」，磁盘仍有残留。
3. `delete_session_on_demand` 不删除 `.gsa/sessions/<s8>.lease`，「彻底移除」的文案不准确（P3）。

**建议**：CLI `delete-session` 改走 `_orz/session_delete` 同语义的 host 原语：先 lease 探测（`lease_conflict`）→ 若 active 则 `session_busy` → close → 删 → 墓碑；或至少加 lease/run 检查并在失败时保留可重试状态。删除循环改为「先收集、逐件记录失败、最后汇总」，不要 `?` 中断。补一条「第二进程持 lease 时 CLI delete 被拒」的测试（现有 `second_process_gets_lease_conflict` 只测 close，不测 delete/CLI）。

### 4.1 桥的请求 id 双向混表 → `prompt_in_flight` 卡死 → Web 锁在「运行中」

**事实**：
- `acp_pump.rs:197` 只有一张 `requests: Mutex<HashMap<u64, String>>`；`observe_agent_frame`（202-225）把 **agent→client 请求**（`session/request_permission`）也插入同一张表；`observe_client_frame`（261-277）只记录 client→agent 请求；客户端的 permission **响应**没有 `method`，不会被移除。
- agent 侧 `agent-client-protocol 0.10.4` 的 `rpc.rs:88,118` 请求 id 从 **0** 起；Web `acp.js:12,37` 的 `nextId` 从 **1** 起。两侧 id 空间独立但值域重叠。
- 时序：client `session/prompt` id=3 在途 → agent 第 4 个 permission 请求 id=3 → `observe_agent_frame` 用 `3 → session/request_permission` 覆盖 `3 → session/prompt` → agent 对 prompt 的响应 id=3 到达，`remove(3)` 返回 permission → `prompt_in_flight` **永不清零**；permission 条目也永久泄漏。
- 刷新后 `claim_attachment` 把 `prompt_in_flight: true` 写进 preamble；`main.js:1679-1682` 先 `vm.setRunning(true)`，再 `await resyncBusyState()`；而 `resyncBusyState` 首行是 `if (state.running) return`（`main.js:238`），必然早退。后续 journal 终态只做历史投影，**不写 `state.running`**（`state.js:361-367` 注释与实现），于是 UI 永久「运行中」。
- 卡住后的连锁：`submitPrompt` 见 `state.running` 就把输入转 `queueSupplement`（`main.js:263-268`），队列无人 drain；`syncToolbar` 用 `state.running` 禁用「新建会话」「关闭会话」（`state.js:402/404-405`）；`stopRun` 只发 cancel（无实际 run），`newSession`/`closeSession` 被禁用。**用户只能重启桥或放弃当前页**；刷新会再次 attach 到同一个 `prompt_in_flight=true` 的事实，仍锁死。

**可信度**：静态时序为高置信；没有单测覆盖 id 碰撞（`acp_pump.rs:830-955` 直接测 `claim_attachment`，不经过 `AgentBridge.attach`）。`54d12bcc` 这类真实 run 有 17 次 `permission_requested`（§1.3），说明长会话跨越 id 空间很常见；若其中只有一部分经 ACP 网关弹出，也足以在多次运行后命中。

**建议**：client/agent 分两张表，只追踪 client→agent 请求；permission 请求单独存「未应答队列」供 attach 重放；补一条「client prompt id 与 agent permission id 相同」的单测。另修 `onBridgeAttached` 的顺序：先 `resyncBusyState`（此时 `state.running` 尚为 false）再按真实结果置态，不要让 resync 自废。

### 4.2 锁序反转：`queue_append`/`recall_preview` 与 close/evict 互为反向

**事实**：
- `handle_queue_append`：先持 `runs`（`acp_server.rs:5321-5324`），再取 `sessions`（5330-5334）。
- `handle_recall_preview`：先持 `runs`（5369-5373），再取 `sessions`（5379-5390）。
- 反向路径：`release_session`（5040-5064）、`evict_over_cap`（5080-5089）、`lifecycle_state`（4917-4928）都是先 `sessions` 再 `runs`；332 档 §2.2 还明确写「sessions→runs 锁序」。
- 这是标准 ABBA 资源序反转；332 的自述锁序与实现不一致。

**影响**：当前 `orz --stdio`/codex 入口都在 `LocalSet` + `spawn_local`（`orz-bin/src/main.rs:702-703`、`stdio.rs:358-360`），锁段内无 `.await`，同线程串行时死锁暂不显现；一旦换多线程 runtime、把 handler 放进 `tokio::spawn`，或在同一 `LocalSet` 里出现锁段 await，`queue_append` 与 close/evict 并发即互等。属**潜伏 P0/P1**，现在修成本极低。

**建议**：统一为 `sessions → runs`：`queue_append` 先在 sessions 锁内克隆 `Arc<SupplementQueue>` 再释放，然后取 runs；`recall_preview` 同理。或给两个锁定级并在 debug 断言。补一条并发测试（可用多线程 runtime 触发）。

### 4.3 状态机只落了一半：`closing` 不可达、`archived` 未构造、通知只发 closed、`SessionCommand` 未使用

**事实**：
- `closing`：`acp_server.rs:5060` 设 `session.closing = true`，下一行 `5061` 就 `sessions.remove`；`lifecycle_state`（4922-4923）只在行还在表里时才能读 `closing`，而 `prompt` 的 `closing` 拒绝（4112-4119）与 `release_session` 的 `closing` 检查（5047-5049）因此都是死路径。`session_ops.rs:322-328` 的 `Closing → invalid_state` 分支同样不可达。
- `archived`：`SessionState::Archived` 全仓无构造点（`rg` 仅枚举/匹配）；0cy sweep 后会话是「包在、侧车无、`.closed` 无」，`state_of` 会走 `None → not_found`（`session_ops.rs:349-366`），而不是 `archived`；`_orz/session_delete` 对 sweep 归卷的会话也就删不掉（设计 §3.2 恰允许 delete archived）。
- 通知：`emit_session_state` 唯一调用点是 `finish_closed`（`5000`）；created/idle/active/closing/deleted 的转移都不发。设计 §4 不变量 8 是「每次转移发 `_orz/session_state`」。

**影响**：Web 的 `on('state')` 只能感知 closed（用于驱逐/关闭解绑）；archive/restore 仍不在新状态机内；「单一 owner」和「底座可换」都只是半个抽象。对用户最直接的是：`closing` 期间的新 prompt 不会被明确拒绝，而会在 `release` 时得到 `session_busy`；`session_state` 查询看不到「正在关闭」。

**建议**：要么把 `closing` 做成真实可查询状态（保留行、置 `closing`、close 完成再移除，并更新 `lifecycle_state`/prompt 拒绝/通知），要么从 331 的公开状态机删除；`archived` 二选一（接到 `SessionState` 或从设计删除）。`emit_session_state` 至少覆盖 created/active/idle/closed/deleted。`SessionCommand` 要么接线（stdio → command → session_ops），要么删除并在 331 §5.1/§11 登记「适配器未按命令枚举实现」。

### 4.4 错误码与四要素只在 close/state/delete 的 ext 面成立

**事实**：

**建议**：把 `AcpError::InvalidRequest`/`SessionNotFound`/`SessionLifecycle` 在 stdio 的 prompt/load/queue/recall 路径统一映射为带 `data` 的四要素；`copy.js` 的 permission/provider 项要么接上真实生产者，要么标注「预留」。补一条「删除后 prompt」的 rust+smoke 链式测试。

### 4.5 跨工作区会话在 attach 时丢根（且工作区切换后槽身份不变）

**事实**：
- `server.rs:367-368`：`/ws/acp` 用**当前 cwd** 作 bridge key，完全忽略 `TokenQuery.root`。
- `acp_pump.rs:398-400`：attach 前置帧的 `cwd` 是 `attach(key, cwd)` 的 `cwd`，即 **child 启动 cwd**，不是会话的 `base_dir`。
- 会话可以来自另一个根：`ui.resumeConversation` 的 `resolveLoadCwd` 优先用 `target.root`（`main.js:87-103`），`session/load` 带 A 根，但 child 仍是在 B 根 spawn 的；`handle_session_load_with_options` 接受 A 并把它作为会话 `base_dir`（`acp_server.rs:3934-4008`）。
- 刷新后：`onBridgeAttached` 用 `params.cwd`（B）`setBinding`（`main.js:1678-1683`）。`syncLiveTail`/`fetchRecall` 随后按 B 找 A 的 runs/侧车，历史尾部与撤回水位丢失；若用户先切到 A 再刷新，key=A → 新 child，原 child 里的活会话根本 attach 不到（旧 child 保活到 grace，但页面看不到）。
- 工作区切换 + 新建会话：`switchWorkspaceTo` 不重连 WS（`main.js:1264-1305`），`ui.newSession` 在同一旧 child 上以新 cwd 发 `session/new`；之后刷新 key=新 cwd → 新 child，刚建的会话留在旧 child 中，刷新即「未恢复」。

**影响**：这是 329 保活对 0bv 工作区切换的回归：`server.rs:359-361` 仍写「新区可在自身 cwd 下开新会话」，但 keepalive 让 WS 不再关闭，新会话不会 spawn 新 child。跨区恢复/切区后刷新都会出现「历史/撤回读数按错根」「活会话失联」。

**建议**：桥在 `session/new|load` 的请求参数里记 `session_root`（或从响应/会话表回读 `base_dir`），preamble 回传 `session_root`；`/ws/acp` 的 key 不应只由当前 cwd 决定，至少要在「已绑定会话的根 ≠ 当前 cwd」时优先用会话根，或在工作区切换时显式重连/换槽。补一条「A 根会话在 B 根 child 中 load → 刷新 → attach」的单测。

### 4.6 审批帧跨连接丢失（刷新后最多等 300s fail-closed）

**事实**：
- `acp_pump.rs:281-292` 的 `deliver` 只把帧发给当前 sink 或 detached backlog；`run_connection` 的 `ingress` 消费后即离开 backlog。permission 请求**已投给旧 WS** 后刷新，旧页消失，该帧不在 backlog（backlog 只缓存 detached 期），新页收不到。
- agent 侧 permission 等待有 `PERMISSION_PROMPT_TIMEOUT = 300s`（`orz-host/src/permission.rs:47,322`），不是永久挂死；但用户会看到「运行中」卡 5 分钟后被 deny，且新页没有「审批丢失」的提示。
- 8 MiB backlog 溢出（`acp_pump.rs:160-176`）也会丢 permission；`truncated` 文案只说「输出帧已丢弃」。

**影响**：刷新/长断线正好落在审批弹窗上时，用户以为「重连后继续」，实际要等 5 分钟；若同时命中 §4.1 的假运行态，输入还会被转队列。329 档 §2.2 未登记这条。

**建议**：桥保留「未应答的 agent→client 请求」，attach 时重放（或在 detach 时回 `cancelled` 并让 agent fail-closed）；permission 请求单独计数并在 `truncated` 时提示「审批可能已丢失」。补一条「permission 已投递 → detach → attach」的单测。

### 4.7 上下文估算与 orz-loop 不同口径，「同源」声明不实

**事实**：
- `context.rs:44-56` 只对 sidecar `messages[].content` 做 `chars` 求和，再整体 `/2`。
- `orz-loop/src/compact.rs:637-649` 的 `estimate_message_tokens` 还累加 `reasoning_content` 与每个 `tool_calls` 的 `name`＋`arguments` JSON 字符，再按**每条消息** `/2`。
- 333 §2.4/§4.2 与 `context.rs:7-9` 头注写「与 orz-loop 估算口径同源/同口径」——**不成立**；工具密集或推理密集会话会明显低报。此外两侧都**不含**系统 preamble/滑块外携带内容，所以「估算占用」本身也不是请求的真实上下文量。

**影响**：S9 的必闭要求是「可读读数」，近似可以接受；但把「非同一函数」写成「同口径」会让后续决策（例如拿它判断 900K 水位）失真。

**建议**：直接复用 `orz_loop` 的估算函数（或镜像其字段与逐条 `/2`），把 `estimate_method` 写成「消息正文+推理+工具调用 chars/2，不含系统 preamble」；UI 加一行「与真实 tokenizer 的偏差」。补一条「含 tool_calls/reasoning 的 sidecar」对拍测试。

### 4.8 doctor 面窄于 330 必闭第 8 条，且 runs 节不是「最近终态」

**事实**：

### 4.9 删除语义与设计相反：idle 可删、sweep-archived 删不掉、load 早退绕过墓碑

**事实**：

**建议**：把 delete 的源状态收敛到设计（或明确改设计并登记「idle 可删」）；`state_of` 需要能表示 `archived`（至少看包），否则 delete archived 无解；load 早退前加 tombstone 检查。补 `delete archived`、`delete idle`、`delete after out-of-process tombstone` 三条测试。

### 4.10 队列/后台读数：切会话不清零、后台计数不是任务数

**事实**：

### 4.11 `/rewind` 重放过滤依赖完整事件窗（200 run 上限/64 MiB/20 万事件）

**事实**：
- `filterEventsByRecall`（`main.js:582-620`）按「事件流中第 k 个用户事件」截断；`ordered` 来自 `state.runs`，而 `runs.rs:27` 的 `LIST_CAP=200` 是全工作区共享的列表上限，`journal.js:22,35` 单 run 还有 64 MiB 截断；`RECALL_FILTER_MAX_EVENTS=200000`（`main.js:574`）只是事件数上限。
- 若窗口从撤回目标之后开始（>200 run 或 tail 截断），第 k 个用户事件落在更晚的事件上，可能把服务端保留的 run 裁掉；若 k 不可达则不裁，被撤 tail 又会显示。329 档 §2.1 的残留边界只写了「>20 万事件」，没有写 200 run / 64 MiB。
- 撤回窗口之外的失败/取消 run 的 `prompt_submitted` 只存在于 journal（侧车只在成功 run 后落盘，`acp_server.rs:4502` 注释「失败/取消路径不更新 sidecar」），本地 ordinal 与侧车 ordinal 可能差 1；当前 `cut<0` 只提示不截断，属诚实降级，但 `filterEventsByRecall` 在重放时仍按事件计数，可能产生「跨撤回点的错裁」。

**影响**：长会话（>200 run）或超长 journal 的撤回投影不是「精确」而是「窗口内近似」；329 的「重放不让撤回 tail 复活」在这些边界下不成立。

**建议**：`recall_log` 回传**水位锚**（`run_id`/`sequence` 或 `remaining_messages`/`recalled_at` 的 journal 锚），前端按锚过滤并检测「窗口起点晚于锚」时显式拒绝过滤；把 200 run/64 MiB 写进 329/S6 的残留边界；补一条「窗口缺前半段」的 smoke。

### 4.12 attached 期 ingress 无界（8 MiB 只约束 detached backlog）

**事实**：`claim_attachment` 建的是 `mpsc::unbounded_channel()`（`acp_pump.rs:378`），`deliver` 用 `sink.send` 不阻塞（281-292）；`run_connection` 逐帧 `ws_sink.send(...).await`（657-666）。慢/半开 WS 时 agent 输出可在 channel 内无限增长，8 MiB 只作用于 `SlotState.backlog`（49,158-176）。`MAX_ACP_LINE_BYTES` 还是 64 MiB（43），单帧也能很大。

**影响**：本地环回 + 令牌门，恶意面有限；但长构建日志 + 浏览器卡顿/休眠可以吃掉桥内存，不是「有界」设计声称的形态。

**建议**：attached 期也用有界 channel（例如 8 MiB/帧数上限），满时丢最旧并置 `truncated`，把同样的 `_orz/bridge_backlog_truncated` 通知给当前页。
