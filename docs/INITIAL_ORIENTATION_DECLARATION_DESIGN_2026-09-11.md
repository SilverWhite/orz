## 1. 问题（O1）

框架不校验「**正在优化的量**」与「**验收判定的量**」是否同一口径，也不校验
「当前做法是不是最短路径」。TB 4.0 探针里这两个缺口同时发生：agent 以纯 IP 规则
剔除机器人后统计点击率，得出 4.0182% 并据此收敛到 `ad_load=0.25`；而验收以
「最终配置 + 疲劳重放」解析计算，得 0.4363%（差 9.2 倍）。收尾的反例门只检验了
**同一把尺子下**的敏感性（含/不含机器人、不同停留阈值），从未质疑尺子本身。

同源问题在本项目自身也有先例：**过度自制**——本该复用成熟组件却自行长路自建，
方向偏移在投入大量工时后才被纠正。

## 2. 用户裁决与设计原则（2026-09-11）

1. **不在周期问询里加这一问**。若把它挂到周期性中立问询上，会让模型在动作过程中
   **反复质疑**自己，干扰动作。
2. **大方向上的决定与设计应当一开始就完成**；动作过程中的中立问询只承担
   **回看与确定**，不承担回查与质疑。
3. **即便中途需要二次决策，也不应表现为"回查和质疑"**。
4. 因此 O1 的正确形态是：**开局先做一次判断**——在中立问询机制下开一个**小的
   额外设计**，在**首轮动作批次结束**时一次性请求模型判断当前实际任务的
   **口径、方向与做法评估**。
5. **二轮复核（2026-09-11）**：时机取 B（首轮动作批次结束注入），但**不携带机械
   审查报告**——审查依旧是结尾的事。理由是报告自身的设计纪律：机械审查报告
   **「不给建议、不注入运行中反馈」**，内容收敛为「执行事实 / 预算 / 异常事实」
   三类（`orz-loop/src/mechanical_audit.rs` 头部注释），不该掺入问询。
6. **问询哲学（用户口径）**：「就像安全行业的检查需要一边说一边动作一样，
   **只要让模型想了那就足够**」——不校验回答、不因回答触发额外轮次。

## 3. 设计

### 3.1 一句话定义

**初始轮中立问询** = 复用既有中立问询（orientation）的**软门语义、票据、事件面与
pending 软消费机制**，在**首轮动作批次结束时**机械注入一次三问、随该批工具结果
交给模型；一次性，此后永不重复。

**载体边界（2026-09-11 二轮裁定）**：**不携带机械审查报告**。理由：

- 机械审查报告 `[MECHANICAL_AUDIT v0.1]` 的设计纪律是**「不给建议、不注入运行中
  反馈」**、内容收敛为「执行事实 / 预算 / 异常事实」三类
  （`orz-loop/src/mechanical_audit.rs` 头部注释）；掺入问询会污染其定性。
- 该报告**目前只有一个注入点**——模型**第一次不调用工具、准备交答案**的那一刻
  （`orz-loop/src/agent_loop.rs:2141-2185`，`once_only: true`、
  `position: "final_answer"`）。长任务里它会晚到收尾：TB 4.0 探针中模型从第 1 轮
  调工具到第 776 轮，报告与反例质询直到全部工作完成后才出现（事件序号 7078）。
- ⇒ **审查依旧是结尾的事**；本问询独立注入，只借用"首轮动作批次结束"这个时机。

### 3.2 触发

| 项 | 定义 |
|---|---|
| 触发类型 | `initial_round`（新增；既有为 `completed_turns_interval` / `pre_handoff`） |
| 触发条件 | **首轮动作批次结束**——第一轮模型输出产生至少一次工具调用、且该批工具结果已全部返回 |
| 注入位置 | **`post_tool_batch_gap`**（既有两个中立问询注入点之一：工具结果已到、下一次生成未开始），以**机械注入文本**随该批结果交给模型；**独立块**，不并入机械审查报告 |
| 频次 | **会话内恰好一次**。与阈值 50 的周期问询互不影响、互不重置 |
| 并发闸 | 沿用既有 **单一 pending 闸**：同一时刻只允许一个 pending checkpoint；本问询未消费前不触发周期问询 |
| 无工具批次（**用户已认可**） | 若首轮模型输出**没有**工具调用（纯文本回复），不在该轮触发；顺延到**首个含工具调用的批次结束**后再注入（避免打断"先回答"的回合） |
| 机械审查报告 | **完全不动**：既有终答前 `[MECHANICAL_AUDIT]` + `[COUNTEREXAMPLE_GATE]` 注入保持原样，**审查只在结尾**、不携带本问询 |

### 3.3 三问（块 `[INITIAL_ROUND_INQUIRY v0.1]`，用户口径原文）

与既有 `ORIENTATION_BLOCK v0.4` 并列、**独立常量**（不复用、不改写周期问询的三问）。
一次性、独立块、随首轮动作批次结果注入：

```
[INITIAL_ROUND_INQUIRY v0.1]
开局问询（一次性，非强制模板，不打断动作）：
1. 本任务实际要交付什么、会被按什么判定？
2. 大方向是什么？当前处在什么阶段、下一步要解决什么？
3. 当前做法优劣如何？你对任务有何评估？
[/INITIAL_ROUND_INQUIRY]
```

**问句设计取舍（记录，避免后续被"更详细"的冲动改回去）**：

- 首版草稿的第 3 问曾写成「有没有更短路径？**为什么没有选它？**」——经用户指出，
  这是**追责式**提问，属于"动作中的回查与质疑"，与 §2 原则相悖；改为现行的
  「**当前做法优劣如何？你对任务有何评估？**」——是**要评估**，不是**要交代**。
- **问句保持简短**：不再追加"请写明判定标准/数据来源/为什么"一类展开要求。
  依据用户口径：「就像安全行业的检查需要一边说一边动作一样，**只要让模型想了
  那就足够**」。
- 措辞纪律：用"问询 / 评估"，不用"检查 / 复核 / 是否搞错"；不要求自证、不要求
  反驳、**不设结构化字段强制**；不因回答内容触发额外轮次。

### 3.4 软门语义（沿用，不新增）

- 不阻断工具、不设模板校验、不禁止工具调用；纯文本回答被消费后 loop 明确续跑，
  终答仍只由模型自发（沿 THIN-HARNESS-REDESIGN-V2 §9.2 主车道延迟 commit 软门）。
- 事件先行、commit 在后：journal 写入失败不得留下"已 reset 未 fire"的计数
  （沿 review P2-2）。
- **恢复语义**：fire 后未被消费即中断（传输错误/取消/panic），计数不提交，
  下次 run 在 `loop_top_gap` 首轮重触发——沿既有 recovery-resumes-counting；
  孤儿事件由运行终止事件解释，不补机制。

### 3.5 与既有机制的分工（不重叠）

| 机制 | 时机 | 职责 |
|---|---|---|
| **初始轮问询（本设计）** | 首轮动作结束，一次 | 开局**定**口径、方向、做法 |
| 周期中立问询（现状） | 每 50 个模型轮 | **回看与确定**（三问保持现状，不质疑） |
| 反例门（现状） | 计划/正式结论写入前一次 | 结论前的反例检查 |

## 4. 非目标

- **不改**周期中立问询的三问与阈值（保持 §2 原则 2：动作中只回看与确定）。
- **不新增**硬门、不新增工具、不改工具面、不改轮次预算。
- **不要求**结构化回答字段，不把"是否答对"变成评分或拦截条件。
- 不做任何"质疑型"追问；不因回答内容触发额外轮次。
- **不落黑板锚点**（用户 2026-09-11 裁决）：实际使用中只要该问询能被触发，后续会
  有新的讨论与询问，届时再决策；**不把旧的审查内容长期留在黑板上**。
- **不额外设计消费审计**（用户 2026-09-11 裁决）：只要问询被触发、模型想了就够；
  再单独记录"是否已被消费/已作答"属多余。
- **不改**既有终答前的审查报告 + 反例质询注入，**也不把问询并入该报告**——
  **审查依旧是结尾的事**（用户二轮裁定）。

## 6. 成本与收益

- **成本**：每会话 **+1 次模型调用**（一次性，随任务规模摊薄）；无新增常驻 token；
  无工具面变化。首轮问询的回答会短暂占用上下文（一句话量级）。
- **收益**：把"口径 / 方向 / 做法"的判断前置到开局——正是 O1 命中场景
  （代理指标 ≠ 验收口径）与"过度自制"类方向偏移的**最早可拦截点**。
  按 TB 4.0 探针的代价换算，一次拦截可省数小时墙钟与数千万 tokens。

## 7. 裁决记录（已全部定案，无待裁决项）
