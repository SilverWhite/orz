## 1. 目的与范围

本稿不新开路径议题。§9 的路径裁决（本地分段检索 = SERP 引擎链 → 逐页抓取 → 逐段抽取，纯 HTTP）不变；本稿只登记**裁决与当前实现之间的四处缺口**，外加一处待复验的观察。

1. **G1 计时语义**：裁决说「10 s 是首个结果上限，总预算另一本账」，实现对不上。
2. **G2 降级页判定**：引擎返回 HTTP 200 但内容是无关热门站时，现在被判成成功。
3. **G3 引擎面收尾**：代理形态下会启用 google/duckduckgo，它们的跳转包装没有处理。
4. **G4 代理管道**：§9.6② 已裁决「有代理时模型自选引擎」，但代码里没有任何代理管道。
5. **G5（待复验）**：无头/有头对 SERP 质量的影响，仅登记观察，不改默认值。

§10（2026-09-15）已对上列缺口作出裁决并定下落码顺序 **G2 → G1 → G3 → G4**；本稿自 v1.0 起可作实施基线（裁决依据与偏离登记见 §10，未决/复验条件见 §10.7）。

非目标：不改工具面与提示词；不改事件契约与稳定码闭枚举；不改 TB 2.1 口径四要素；不把浏览器依赖引入分段检索路径。

## 2. 一手证据（2026-09-14/15，本机实测）

同一台机器、同一查询（`DeepSeek Responses API web_search ignored`，属冷门长尾技术查询）：

| 观测 | 读数 |
|---|---|
| 裸 HTTP 取 Bing SERP | 5/5 样本为**无关热门站**（4399 游戏、Steam、知乎、四六级、阿里云） |
| 真浏览器取 Bing SERP（有头） | 4/4 样本相关（linux.do「0910 跟 V4.1F 一起改的，Responses API 服务端联网搜索 web_search 全部下架」等） |
| 真浏览器取 Bing SERP（无头） | 0/5 相关 |
| 代理 `127.0.0.1:7890` 下 DDG 直取 | 200 / 35 KB / 10 条命中 / 1.0 s，相关 |
| 代理下 Google 直取 | 200 / 92 KB（纯 HTTP 为 consent 页；真浏览器去掉 `--enable-automation` 后为正常 SERP） |
| 九条跳转包装**串行**解析 | 130 s（Google）/ 86 s（Baidu） |
| 九条跳转包装**并发**解析（8 线程，6 s 超时） | 约 20 s |
| 一次浏览器形态检索端到端 | **20–27 s**（启动 + 导航 + 渲染 + 解析 + 抓正文） |

两条推论,直接决定下面四个缺口：

1. **「非空即成功」在本机不成立**：引擎会给整页无关结果,结构化解析完全正常(`b_algo` 十条俱在),`hits.is_empty()` 永远为假。
2. **10 s 装不下浏览器形态**：SERP + 逐页抓取共用一个 `engine_started`（`local_segmented.rs:568` 与 `local_segmented.rs:617-628`，均在 `crates/codegen/orz-tools/src/implementations/web_search/`），实测首测即 `Page.goto: Timeout 10000ms exceeded`。

## 3. G1：计时语义（裁决已定，实现未对齐）

### 3.1 现状

`search()` 逐引擎计算 `budget = per_engine_deadline.min(remaining)`，然后 `tokio::time::timeout(budget, fetch_engine(...))`；`fetch_engine` 顶部重置 `engine_started`，把 **SERP 请求 + 解析 + 最多 `segment_pages` 次页面抓取**都记进这一条钟。即：裁决里的「首个结果上限」目前实际上是「首个结果 + 三段正文」的上限。

### 3.2 设计

把一本账拆成三段，各自独立计时，整体兜底不变：

```text
T_acquire   取浏览器/建连/预热     —— 不算检索预算（准备阶段）
T_first     发起检索 URL → 首个可解析结果   ← 裁决所指的 10 s 落在这里
T_segment   逐页抓取 → 逐段抽取     —— 每页独立预算，不占 T_first
T_overall   整体兜底（不变，默认 30 s，可配 ORZ_RETRIEVAL_OVERALL_DEADLINE_MS）
```

要点：

* `T_first` 的起点 = **请求发出**（HTTP 形态=请求 send；浏览器形态=导航发起），与裁决原文一致。
* 建连/预热耗时记入 `T_acquire`（HTTP 形态 = 专用客户端的 `connect_timeout`），失败落 `capability_unreachable`，不与检索超时混码。
* 段抽取超时不再判成「检索失败」：SERP 命中照常交付（现行代码已按「页级失败不致命」处理，本稿只是把它从 `T_first` 里挪出去）。
* 可配项沿用现名前缀（§3.3 裁决）：`ORZ_RETRIEVAL_ACQUIRE_MS`（默认 5 000）、`ORZ_RETRIEVAL_SEGMENT_MS`（默认 10 000）；`ORZ_RETRIEVAL_DEADLINE_MS` 语义收窄为 `T_first`。

### 3.3 裁决（2026-09-15，用户授权工程裁决）

| 预算 | 默认值 | 落点 | 依据 |
|---|---|---|---|
| `T_first` | **10 s**（不变） | 每引擎：请求 `send()` → 首个可解析结果（`tokio::time::timeout` 只包这一段） | 承前裁决原文；机器合约判据「检索类首个结果 `wall_ms` p99 ≤ 10 s」按此校准，改默认值等于悄悄放宽判据。默认引擎 `cn.bing.com` 直连 TTFB 实测 0.4 s（§2 / S1′），10 s 是 25× 余量。冷启 DDG（TTFB 11 s）只在显式代理 + 显式选 DDG 时出现，用 `ORZ_RETRIEVAL_DEADLINE_MS` 行内放宽即可，不进默认。 |
| `T_acquire` | **5 s**（本稿原建议 30 s，**下调**） | `local_http` 专用客户端（`build_http_client`）的 `connect_timeout`；现行代码已是 5 s，本裁决把它升为**登记口径** + `ORZ_RETRIEVAL_ACQUIRE_MS` 可配 | 分段检索是纯 HTTP：`reqwest::Client` 在装配期建好，acquire 只剩建连/DNS/TLS（实测亚秒级）。30 s 会让一次挂死的建连吃掉整本 30 s 整体预算且零信息产出——正是本稿 §2 要治的「正常等待后才返回」。5 s 保证「确定性不可达」在 5 s 内落 `capability_unreachable`。 |
| `T_segment` | **10 s / 页**（本稿原建议 15 s，**下调**） | 单页 `fetch_page_text` 的 `timeout`，页级预算 = `min(T_segment, 剩余整体)` | 本稿原建议与整体兜底自相矛盾：3 页 × 15 s = 45 s > 30 s，是拿不到的数。10 s × 3 页 = 30 s 与整体同阶。段抽取只是给**已解析出的** SERP 命中补正文（页级失败不致命，现行语义），不值得挤掉交付。 |
| `T_overall` | **30 s**（不变） | `search()` 入口起算的全程硬上限 | 承前裁决原文。语义收窄并写明：**三段预算都从属于它**，任一阶段耗时都扣减剩余整体预算。 |

计时语义收口（与 §3.2 一致）：`T_first` 的**起点仍是「请求发出」**（承前裁决原文）；HTTP 形态下建连阶段由专用客户端的 `connect_timeout` 界定（`T_acquire` = 5 s），请求发起到首个结果由 per-engine 钟界定（`T_first` = 10 s）——两者时间上相邻，按**先到者**归因：建连超 5 s ⇒ `capability_unreachable`（detail 带阶段读数）、建连完成到不了首个结果 ⇒ `network_no_response`、页级抓取超时 ⇒ 页级失败（不改变已解析命中的交付）。

偏离登记：本稿 §10（v0.1）原建议 `T_acquire 30 s` / `T_segment 15 s`，本裁决下调为 `5 s` / `10 s`（**工程裁决，非用户否决**，理由见上表）。三值全部 env 可配，S4 复验可按实测读数再调。

## 4. G2：降级页判定（相关性闸门）

### 4.1 问题

`fetch_engine` 只在 `hits.is_empty()` 时返 `empty_result`；非空即 `ok`。而 §2 实测的降级页结构完整、`b_algo` 齐备，因此**现行实现会把整页无关站当成检索成功交付给模型**。这不是慢，是「看起来成功的错」，优先级高于任何提速。

### 4.2 设计（最小形态）

* 位置：解析成功之后、`ok` 返回之前。
* 判据：取**前 3 条**的 `title + snippet`，与查询词做集合交集。查询词集 `Q` = ASCII 长度 ≥3 的词（小写化）+ CJK 二元组（bigram），去重保序；要求命中数 ≥ `max(1, ceil(0.25 × min(|Q|, 12)))`。
* **词集封顶 12（本裁决新增）**：长自然语言查询（研究型 agent 的常态）若拿全词集当分母，阈值会退化成「必须命中十几个词」= 过严误杀。封顶后长查询的判据 = **命中 ≥3 个**；而引擎兜底页（§2 实测：4399 游戏 / Steam / 知乎 / 四六级 / 阿里云）对技术查询的重叠实测为 **0**，判别力仍足够。宽口径执法（F-007(a)）要求宁可放过、不可误杀。
* 不达标：**复用既有闭枚举**的 `empty_result`，`detail` 写明「SERP 命中与查询无关（引擎兜底页，非解析故障）」，并附 `engine` 与命中分数，供 A/B 与法官核对。**不新增稳定码。**
* 取前 3 条而非首条的原因：本地化短标题（如「DeepSeekV4 怎么用?」）会让首条判据过严，而取三条仍能把「整页无关」与「某条不相关」区分开。
* 开关：`ORZ_RETRIEVAL_RELEVANCE_GATE`（0/1）——**裁决：默认 1（开启）**。理由：闸门拦的是「看起来成功的错」（§4.1），属正确性问题而非性能问题，默认关等于把已知缺陷留给复验前的每一次真实检索。关闭时行为与现状完全一致（逐字节基线），供 A/B 与回退。
* 判负后的行为（明确）：按现行 `empty_result` 分支**继续引擎链**（`continue`），`attempts[]` 记该引擎 `empty_result`（detail 带判负分数与 `need`）；全链判负时最终错误 = `empty_result`，detail 取**分数最高**的那次尝试（避免只报最后一个引擎）。

### 4.3 边界

* 纯符号/纯数字查询（如版本号）词集为空时**直接放行**，避免误杀。
* 闸门只判「是否交付」,不改写、不重排、不摘要——与 §9.1「每段独立、不合成」的纪律一致。
* 阈值 25% 与封顶 12 是**首版值**，不是终值：S4 复验按「误杀（真相关被判负）/ 漏放（无关页被交付）」两个方向的实测率再调，调整入口登记在本节。

## 5. G3：引擎面收尾（跳转与真实 URL）

代理形态下 §9.6② 会启用 google/duckduckgo，二者与 Baidu 都有跳转包装：

| 引擎 | 包装形态 | 现行处理 |
|---|---|---|
| bing | `bing.com/ck/a?…&u=a1<base64url>` | 已处理（`normalize_hit_url`） |
| google | `google.com/goto?url=<不透明令牌>` | **未处理** |
| baidu | `baidu.com/link?url=<encoded>` | **未处理**（引擎亦未入集） |

设计：

1. 新增两个解包分支，与现有 `normalize_hit_url` 并列；Google 的令牌不透明，需跟随一次跳转才能得到真实 URL。
2. **并发解析（裁决：6 worker / 单条 6 s）**：串行代价实测 86–130 s / 九条（§2）。**下调本稿 v0.1 建议的 8 worker** 依据：解包只服务于输出可读性，不是交付前置；而 8 路并发打同一批跳转端点会逼近自动化检测面（本机刚实测过 Google `/sorry/`、Brave captcha、Sogou `/antispider/` 三例），一旦触发是**整条引擎链当轮失效**——风险不对称，取 6。九条 ÷ 6 worker ≈ 2 波 × 6 s ≈ 12 s，叠加 `T_first` 10 s 仍落在 30 s 整体兜底内。失败保留包装 URL，不阻断交付。
3. **不新造阶段总预算**：解包整段取 `min(剩余整体预算)`（与页抓取共享同一本账）；参数 env `ORZ_RETRIEVAL_UNWRAP_WORKERS`（默认 6）/ `ORZ_RETRIEVAL_UNWRAP_MS`（默认 6 000，单条）。
4. **抓页回填（优先级最高）**：页面抓取本来就会跟随跳转，`response.geturl()` 可直接回填为交付 URL——零额外请求，且能覆盖并发解析失败的那几条。交付 URL 取值序 = 页抓取回填 > 并发解包 > 包装 URL 原样。
5. 解包与页抓取**并发推进**（同一并发段内启动、段末统一 await），互不阻塞。
6. Google 的结果标题不再裹在普通 `a[href]` 里（现行 DOM），若走浏览器形态需按 DOM 结构取值，不建议再用正则匹配标题锚点。

Baidu 解包分支按上表预置（形态已知、成本低），但 **baidu 是否入引擎集不在本批**（见 §10.7）：入集需另行裁决引擎面与 CJK 默认链序。

## 6. G4：代理管道（口径已定，实现缺）

§9.6② 已裁决「有代理配置时引擎交由模型自选」，但 `web_search/` 与 `local_browser/` 两处**都没有任何代理配置读取**（`reqwest::Client` 直接构建）。

### 6.1 裁决（2026-09-15）

* **不设引擎白名单（用户裁决）**：orz 跑在真机环境，真机上了代理即生效；代理**只影响传输与默认链序**，不新增、不收窄引擎允许集。显式 `ORZ_RETRIEVAL_ENGINES` 永远优先。
* **读取顺序**：`ORZ_RETRIEVAL_PROXY` → `HTTPS_PROXY` → `HTTP_PROXY`；另有 `ORZ_RETRIEVAL_PROXY=none` **显式关闭**（优先级高于三个来源），供容器/评测基线保证与官方口径可比（§9.4「容器无代理不进默认集」继续成立：容器不设代理 env ⇒ 行为与现状逐字节一致）。
* **默认链**：无代理 = `bing_cn` 单引擎（不变）；有代理 = `duckduckgo,google,bing_cn,bing_global`（按实测可达性排序：DDG 走代理 1.0 s 且相关 / Google 走代理返回正常 SERP / Bing 走代理返回 consent·地区页 ⇒ 排后）。四个引擎**都在集内**，故不构成白名单。
* **实现落点**：代理只加在**分段检索专用客户端** `local_http`（`build_http_client`），不动服务端 `/responses` 客户端（其 `default_headers` 带 API key，经代理转发会改变凭证边界）。
* **形态差异登记**：同一代理对不同引擎效果不同（Bing 代理形态降级、DDG 代理形态可用），A/B 记录必须分别留读数；`engine_channel_detail()` 一类读数带 `proxy=on|off` + 端点（脱敏至 `host:port`），让 `retrieval_family` 探针能区分两种形态（与 §10 探针口径同源）。
* 模型自选引擎的**提示词面**属 §9.6② 的后续实施，另开；本批只做传输与默认链序。

## 7. G5：无头/有头（仅登记，不改默认）

§2 实测有头 4/4、无头 0/5。`ORZ_BROWSER_HEADLESS` 默认值若为开，浏览器车道的 SERP 质量可能长期处于降级态**且看起来成功**。建议：在 `retrieval_family` 探针下按现行 fixture 各跑两轮（有头/无头）留读数，再决定是否给**检索用途**单独设一个默认。本稿不提案改默认值，因为该差异尚未在容器内复验。

## 8. 验收与机器核对

沿用本仓既有习惯（改动 + fixture + 法官镜像）：

1. **fixture**：新增降级页样本一件（HTTP 200 + 十条无关 `b_algo`，可脱敏录制）、**真相关对照样本一件**（闸门正例：命中 ≥ `need` 必须放行）、跳转包装样本三件（bing/google/baidu）、边界样本一件（纯版本号查询，验证闸门放行）、**长查询样本一件**（词集 ≥12，验证封顶后判据 = 命中 ≥3）。

### 10.6 落码顺序依据

1. **G2 先行**：纯正确性、零依赖；不修则每次真实检索都可能把整页无关站当成功交付（§4.1），属「看起来成功的错」，优先于任何提速与扩展。
