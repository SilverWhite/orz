## 1. 背景与证据

2026-08-19 S4 单题复验（path-tracing，1800s 预算，deepseek-v4-flash，
`D:\tb-eval\jobs\2026-08-19__04-13-27`）：

- provider 账单口径命中率 **88.84%**（04:00–05:00：hit 1,868,416 /
  miss 234,662 / 47 请求）；对照上次正式运行窗口（02:00–03:00）84.07%——
  提升 4.77pp，仍低于 90% 目标。journal 口径 88.57%（46 请求）。
- miss 归因：**3 次折叠重付 47.8K / 50.4K / 56.4K，合计 154.6K = 总 miss
  的 66.5%**，全部紧跟 `ledger_fold_advance`；黑板的整段读取尖峰（方案 B
  已修）不再出现。
- 机理（实证）：折叠从视图中间移除轮次后，保留尾整体换位，**折叠重付 ≈
  保留尾大小 + 新内容**；本次保留尾（最近 1 轮 + 配对回退轮）实测 44–56K
  真实 token，远大于外挂文件设计 §5 假定的 10–30K。
- 折叠之间的请求为纯追加（miss 137–3.4K，hit 随请求递增），前缀命中机制
  本身正常；无 400。

## 2. 战略裁决（用户 2026-08-19）

1. **折叠本身需要处理**：折叠后其余内容照旧进外挂台账文件，视图只留最新
   桥接（真实 token 预算）；触发维持 128K（用户修正早期 120K 记忆）。
2. **形态甲**：先定裁剪（完整轮边界确定进台账的轮次），再对桥做内容级
   截断到预算；桥 = 最新完整轮（声明 + 全部工具回复结构全保留），超预算
   只截内容 + 指针。
3. **桥 = 8K 真实 token**（默认，可配 `ORZ_FOLD_TAIL_TOKENS`；取值的
   数据依据见 §3.6——桥装得下本次负载下的最新重型轮，截断成为例外而非
   常态；S4 以实测重付与截断频率校准）。
4. **思维链不进桥、不进审计**：审计仅保留 `reasoning_tokens` 计数（成本
   核算必需），不存思维链内容；桥视图剔除 `reasoning_content`——用户裁决：
   思维链具幻觉性，应依靠实际相关数据与机械结果，且存储压力更高。
5. 既有大机制裁决延续：外挂台账文件与行格式、指针消息字节固定、压缩机制
   与白名单、preamble/配对 400 防线全部不动。

## 3. 变更设计

### 3.1 视图结构（取代外挂文件设计 §2.1）

- 未折叠：`messages` 原文（同现状）。
- 已折叠：`[U0][固定指针消息][桥]`。
- **桥** = 最新完整轮（assistant 声明 + 全部工具回复，结构完整、配对
  不变量保持），内容级截断到 `FOLD_TAIL_TOKENS`（8K 真实 token 目标）预算；
  `reasoning_content` 从桥消息中剔除（声明消息仅保留可见 content +
  tool_calls）。
- **桥末端冻结（`bridge_end`，S1 审查处理 N3 补记）**：桥的右端不是
  动态的「消息末尾」，而是最近一次推进时冻结的 `messages.len()`——
  视图 = 固定前缀 + 桥 `[fold_cut..bridge_end)` + 推进后追加轮
  `[bridge_end..]`（原文保留）。折叠之间桥内容固定，请求前缀逐请求纯
  追加、绝不被逐请求重截；下一次推进才重新冻结新桥。这是 §3.6「折叠
  之间仍为纯追加」承诺的机制落点。
- 桥的消息序列整体估算（复用 `estimate_messages_tokens`，字符换算见
  §3.2）≤ 预算；若最新一轮单独超预算，对该轮做内容截断（见 §3.3）使其
  落入预算；预算剩余时按时间从新到旧再容纳更早的完整轮。

### 3.2 裁剪与换算（推进语义，取代外挂文件设计 §2.2「最近 1 轮」）

- `kept_start` 由「最近 1 轮」改为「桥预算内的最新完整轮集合」：
  从最新完整轮往回累加，直至再纳入下一轮会超出桥预算。
- 预算换算：配置按**真实 token 目标**（`fold_tail_tokens = 8_000`）；实现
  以字符预算近似——**S4 实测校准（2026-08-19，path-tracing 07:08 运行）：
  2 字符/真实 token**（第二次折叠桥 12,948 字符 → 折叠后首请求重付
  6,493 真实 token；初始保守值 4 高估一倍，按 §6 DoD 调整为 2）——
  `FOLD_TAIL_CHARS = 8_000 × 2 = 16_000`，估计口径 = chars/2 → 8_000
  估计 token ≈ 8K 真实 token（`estimate_messages_tokens` 估计口径恰好
  近似真实 token 数）。
- `fold_tail_rounds` 语义退役（桥恒含 ≥1 轮的结构，无需轮数下限）；
  `ORZ_FOLD_TAIL_ROUNDS` 不再生效，`ORZ_FOLD_TAIL_TOKENS` 生效。
- 实现决策登记（S1 审查处理 N2）：折叠路径的保留起点由新增 `bridge_cut`
  落地（完整轮累加至预算、最新轮恒入桥、不完整轮回退）；`collapsed_cut`
  保留原语义，仍服务压缩 drain 的 fallback 路径（§2.5「压缩机制不动」）。
  设计 §5 路由「collapsed_cut 改桥预算版」按此理解执行。
- 触发与既有 400 防线不变：loop-top 估算 ≥ 128K（chars/2）、preamble
  校验、`safe_fold_cut` 完整轮/平衡轮检查全部保留；`advance_fold` 的
  「新增轮次入台账」语义不变（入账范围 = `[old_cut .. bridge_start)`）。

### 3.3 桥内容截断规则（形态甲）

- 只截内容、不删消息、不拆轮：桥的消息角色与顺序保持，配对不变量不因
  截断而破坏（任何声明的 call_id 都有其工具回复在场）。
- 声明消息：可见 content 完整保留（通常很短）；`reasoning_content` 剔除；
  `tool_calls` 完整保留。
- 工具回复消息：超限时截断**保留尾部**（最新状态/错误/退出码最相关），
  行首加「…（前略）」+ 指针行「完整内容见 <trace/日志/台账指针>」——
  与「桥=最近内容优先」原则一致；最终回复文本按既有 `truncate_chars`
  口径（头部 199 字符 + 「…」）。
- 中间文本口径（S1 审查处理 O1）：轮内无 `tool_calls` 的 assistant
  文本（含中间说明与最终回复）统一按最终回复口径头部截断（199 + 「…」）；
  带 `tool_calls` 的声明消息可见 content 与 tool_calls 恒完整。
- 截断分配：从旧到新逐消息压缩，直至整桥估算 ≤ 预算；指针行计入预算但
  必须可见（同 `render_notes_capped` 的指针可见纪律）。

### 3.4 指针消息（marker）

- 指针消息保持字节固定（路径固定、文本固定、不含变化 ID）；文案更新为
  「当前会话仅保留最近约 8K 桥接内容，更早轮次已按行归档于 <abs-path>；
  需要回顾历史时按行检索该文件」（保留既有 grep "轮次"/grep <工具名>
  示例，S1 审查处理 N1 后为最终落地文案）——部署首轮一次性指纹变化
  （v1.19 已接受的工具/系统面变化纪律）。
- 配置固定性（S1 审查处理 O3）：`ORZ_FOLD_TAIL_TOKENS` 配为非 8K 时
  指针文案中的「约 8K」不随之改写——文案一次性固定优先于精确表述，
  已接受。

### 3.5 思维链口径（审计）

- journal 审计：维持现状——`model_output` 只记 `reasoning_tokens` /
  `completion_tokens` / `cache_hit_tokens` / `cache_miss_tokens` 计数，
  不存思维链内容；`messages` 全量原文仍在运行时保留（审计双轨不变，
  外挂台账为可确定性重推的机械投影）。
- 桥视图剔除 `reasoning_content` 属视图变换（`build_request_view` 构造新
  消息），不修改 `messages` 本身。

### 3.6 缓存数学与预期

- 折叠重付 ≈ 桥 + 折叠后首请求新内容 ≈ **11–13K**（8K 桥 + 2–5K 新轮）；
  3 窗 ≈ 33–39K（对照现状 154.6K）。S4 实测（2026-08-19 07:08）：2 次
  折叠后首请求重付 **3,742 / 6,493** 真实 token——最新轮（读/计划与执行
  轮）均小于桥预算、无截断，重付远低于 15K 上限。
- 推算：总 miss 234.7K → 约 115K，provider 命中率 88.84% → **约 94%**
  （零折叠成本上限约 95.9%，非折叠 miss 约 80K 为天花板）。S4 实测：
  journal 口径命中率 **95.54%**（hit 4,775,422 / miss 222,869 / 113
  请求），处于推算区间上沿。
- 桥取值依据（实测）：读/计划类轮 ≈ 1–3K 真实 token，终端执行轮 ≈ 5–7K；
  8K 在多数折叠时刻能整轮装下（截断为例外）；4K 命中率仅多约 0.5pp 但会
  频繁截断正常终端轮（连续性成本换命中率不划算）；10K+ 收益递减（最新
  一轮才是锚点，更早内容在台账）。
- 折叠之间仍为纯追加（高命中），方案不改变请求次数/折叠次数。

## 7. 风险与回滚

- **模型连续性**：桥 8K + 黑板上状态面（计划/步骤/订单/结果板不受折叠
  影响）+ 台账行/点读/日志回查兜底；若 S4 观测 reward 退化，调大桥
  （10–12K）或回调保留尾轮数。
- **reasoning 剔除的影响**：模型下一轮将不带最近一轮思考链；S4 观测
  任务质量；若明显退化，备选=桥保留最新轮 reasoning（代价：预算被占用，
  需调大桥，登记为可选后续）。
- **400 防线**：截断只作用于消息内容、不删消息不拆轮，配对不变量保持；
  preamble / safe_fold_cut 校验原样保留。
- **索引越界防御**（S1 审查处理 O2）：极端陈旧状态（压缩/恢复后冻结索引
  超过当前消息长度）下 `build_request_view` 已加越界守卫——放弃折叠回
  原文，杜绝切片越界 panic；正常路径由推进/视图两侧防线覆盖、压缩路径
  reset 状态，该守卫为防御性兜底，最坏代价=每窗一次全量视图（低频接受）。
- **回滚**：改动集中于 `collapsed_cut` / `build_request_view` /
  `advance_fold` 三处 + 配置，单提交可逆；最坏代价=每窗口一次全量视图
  （低频，接受）。
